## 二、明确首个切片的完成条件

必须全部完成：

- 账户个人条目与项目 Claim 的范围隔离，旧项目接口保持兼容。
- 主动添加与范围明确的自然语言表达可保存；临时请求不保存，模糊表达只澄清一次，模型归纳不能直接激活。
- 账户使用政策与项目例外，关闭读取、暂停条目和删除语义清楚。
- 原 Conversation 与 Mission 都使用个人上下文，当前指令/项目硬限制优先。
- 保存准确的原话、形成来源、内容版本和使用指针；重要建议可解释使用原因。
- Web/鸿蒙添加、查看、纠正、暂停/撤回和删除读回；原草稿、CAS、同请求恢复不降级。
- 与原 Turn generation、lease、预算、来源及发布事务对接；删除、撤权与迟到回包真实竞争有保护。
- 通过原批准创建 Action，并由原完成服务留下 resultCardId；跨会话能从 Handoff 读回原状态。

候选自动归纳、长时全文召回优化、夜间整理、跨项目经验自动提议和新的后台触发不属于首个发布默认，但数据与权限合同必须能承接 PM-2～4。不能为了先交付而把当前条目永久写成无来源字符串。

## 三、内部阶段 A：范围和失效保护

先验证统一 AgentClaim/Event 增加 ACCOUNT 范围的迁移可行性。

1. 旧行显式回填 PROJECT，保持旧 scopeKey/唯一身份兼容。ACCOUNT 行 projectId 必须为空，不伪造“我的记忆”项目。
2. 所有项目查询显式使用 PROJECT 与已验证 projectId。禁止 `undefined` 导致过滤条件消失；不把空字符串或 null 当作全范围。
3. 账户与项目使用判别联合，数据库加入对应持久约束。列出受影响查询、来源解引用、导出、删除和客户端类型，不只让 tsc 能过。
4. 统一 Claim 若实际迁移面过大，可选择规划中的薄账户表备选；先说明具体调用方和风险，共用事件、准入、血缘、Composer 与清除服务，不复制一套记忆框架。
5. 增加账户记忆策略和项目成员例外。owner 一律从认证会话取得，API 不接受任意 userId 查询别人的内容。
6. 个人修改使用原 User 写锁、CAS、payload hash 和稳定 requestId。业务修订、回执、privacyRevision 及必要失效同事务提交；模型和网络放事务外。
7. 原项目 ClaimCorrection 的 controlSeq/原话定位语义保持；个人偏好不能混入它的“解释纠正”分支。
8. 策略修改与正文删除后的幂等使用最小 UserMemoryControlReceipt，或经核实可承载相同语义的原回执设施；不能误用只关联 Experience/项目的回执表，也不能在回执中永久留存被删正文。具体新增量在架构文档 7.1 节。

此阶段先完成以下负例：跨账号读取、项目查询读到账户行、同 scope/不同 owner 碰撞、旧客户端读取、两端竞争、重复 requestId 但载荷不同、来源不可访问、时间越界无新事件。

## 四、内部阶段 B：原认知与执行链真实消费

重点核对这些实际入口：

- `lib/conversation/investigationService.ts` 和原路由/验证/发布调用方。
- `lib/mission/contextBuilder.ts`、原 Runner、Step/lease/输出事务。
- `lib/memory/digestService.ts`、`hypothesisService.ts`、`claimEffective.ts`、`inputReadSet.ts`。
- `lib/continuity/admission.ts`、`directiveService.ts`、`sourcePolicy.ts`、`invalidation.ts`、`turnCoordination.ts`。
- `lib/experience/injection.ts`、原提案确认、Action/Handoff 与结果回读。

新增个人条目资格与选择服务，共享给 Conversation/Mission。保留个人自述、偏好、项目证据、综合、假设和方法经验的不同 authority。

路由前只可使用不会泄露项目内容的账户默认；来源于项目的个人派生信息必须通过来源与晋升范围检查。账户记忆不自动扩大 allowedProjectIds、researchScope、公开检索词、连接权限或工具白名单。

个人记忆 readSet 至少绑定条目修订、可用性/内容 hash、来源根、账户隐私版本、项目例外版本与 nextBoundary。缓存同时考虑未选中内容的选择版本、问题与输出受众。不能把现有 contextHash 的名字当作覆盖所有新字段的证明。

模型与 embedding 的派发还要验证个人内容的处理许可。项目同意使用云模型不等于账户同意发送个人背景；只允许规则处理时不能向远端发送个人正文。沿原调用守卫和预算处理，不开旁路。

三类变更分开：

- 表达默认改变：后续回答采用，不暂停所有委托。
- 已影响当前判断的背景改变：受影响原消费者重协调，不重置预算。
- 隐私/删除/撤权：同步守卫先阻断旧内容的新派发和新发布，异步清理不能替代此保证。

账户级失效不能只处理当前项目。对所有受影响活跃消费者建立范围集合，仍遵从原锁顺序。旧模型语义结果不跨 generation 发布，原合法工具观察按原资格规则复用；在途外部效果未知时保留 UNKNOWN，不补发创建或伪造撤销。

保持动态工具选择。记忆不足时允许 Agent 在原许可内回原文、检索旧卡片、读文档或核对指标；不要把调查改成固定流程，不增加强制工具调用。

补一个确能影响行为的用例：用户明确偏好先验证关键条件，当前项目缺数据划分。Agent 应先核对划分/基线并提出缺口，不能仅在原答案里换一句开场白。原模型测试可用脚本响应，必须明确标注；真实模型收益另验。

## 五、内部阶段 C：双端和真实结果链

Web 设置增加“我的记忆”入口，使用列表与按需详情；鸿蒙 SettingsTab 接独立页面。不要把现有模型配置表当账户记忆存储。

首屏展示当前条目与添加入口；来源、时间、使用记录和历史按需展开。不增加人格分数、技术标签和大片空详情；不要把所有功能折叠到无法发现。保留项目记忆与全局项目档案的既有入口。

任务中复用“为什么这样建议”与现有生成式 UI，条目动作绑定 owner/id/revision/hash，不让模型输出任意写入按钮。纠正理解与批准业务提案必须是两件事。

编辑失败保留原草稿，冲突展示当前版本，丢回包先读原请求回执；账号切换不串草稿或来源。删除先显示停止使用，再展示内容清除状态，不能以隐藏一行冒充删除完成。

两端操作同一个隔离身份与原对象：Web 添加 → 鸿蒙读回 → 原 Conversation/Mission 消费 → 手机纠正 → Web 原任务接续 → 原批准/Action/完成回执。不能通过直接更新数据库状态为 DONE/SUCCEEDED 来制造业务闭环。

## 六、必须覆盖的来源和隐私路径

原始条目、Claim、Digest、Hypothesis、Artifact、Episode、Experience、待批提案、导出、缓存、向量、设备草稿与通知视图都要核查。不是每条路径都需新表，但任何可重新注入旧内容的路径都不能漏掉。

ACCOUNT 不能用 `sourceUse(null, ...)` 绕过原项目鉴权，也不能把未知 `personal-memory:` 前缀默认允许。项目派生个人条目在原项目撤权/删除后停止使用；用户独立重述需新事件与明确范围，不静默剪断根。

个人上下文生成的共享成果标记隐私依赖，沿原预览/确认机制确认实际披露内容。项目负责人、Widget、小艺、外部工具默认不能直接读取个人原话。首批不自动保存敏感内容，凭据永不进普通记忆。

删除要防止旧内容重新提取：最小不含正文的来源禁止标记、清空全部时的提取起点、暂停后的不补扫语义一起完成。不能只把当前行删掉，随后又从旧聊天重建。用户明确重新添加才形成新的记忆事件。

## 十、PM-2 执行 Prompt：候选理解、使用控制与完整管理

> 在当前 Personal Memory 工作树中完成 PM-2。先核实 PM-1 Gate，复用现有条目、准入、控制回执、readSet 与双端页面。目标是让用户能理解、纠正和决定是否采用候选，而不是增加一个每天必须清空的记忆收件箱。

### A. 候选和晋升合同

1. 核对原 `memorySynthesis`、ClaimEvent 和个人准入的实际扩展点。优先在已经获准的原 Conversation/Mission 输出中生成候选；不为每轮额外启动提取模型。只有用户发起整理或原责任允许整理时，才使用原调用与预算继续。
2. 候选有稳定身份、revision、内容 hash、原话定位、来源 manifest、条件、例外、建议使用范围、状态与时间边界。不同摘要引用同一原根时不增加“支持次数”。
3. 用户可确认、编辑后确认、仅保留在本项目、拒绝或停止此类提议。确认冻结 `candidateId + candidateRevision + contentHash + originManifest + targetUseScope + expectedPolicyVersion`；服务端再核验当前来源与权限，不能仅收一个 `confirmed=true`。
4. 旧预览、旧政策或来源变更返回明确冲突并保留草稿。同 requestId 同载荷回放原回执，换载荷拒绝；两端竞争只激活一次。
5. 明确添加不依赖开启候选推断。候选推断默认关闭；启用时说明处理范围和提取起点，不自动导入旧聊天。暂停期间的历史不在重开后补扫。
6. 拒绝与冷却按候选含义、条件及来源识别，不仅按文案字符串。没有新证据或实质条件变化时，不改写一句话再次催问；重要新变化可以形成可说明差异的新候选。
7. 不把设备限制归纳为永久兴趣，不自动保存健康、财务、身份等敏感画像；密码、Token、私钥不进入普通记忆。模型不能用多次操作、沉默、已读或采纳率替代确认。

### B. 使用记录、清除与管理服务

1. 使用记录复用 Turn/Step/AgentRun 元数据，区分“检索到”“放入模型上下文”“被模型关联引用”“建议被采纳”和“产生可核验结果”。无法证明后续阶段时显示未确认，不把 prompt 中出现过算成真正有效。
2. 提供按条目、任务和时间分页的最小可核对指针。源任务失权后不泄露标题或片段；删除后不在记录正文、日志和回执中保留个人内容。
3. 完成账户政策、项目例外、候选管理、暂停/恢复、纠正、删除、导出和清除状态的真实服务。优先复用原接口；确需新增接口时统一错误映射及 Web/鸿蒙共享契约，不只增加客户端本地状态。
4. 导出限定认证 owner 和当前可导出范围，说明哪些是用户自述、候选、失效历史。用户主动导出其有权保留的停用历史，不等于允许 Agent 再使用；删除、撤权内容和无权项目片段不得随之导出。旧导出不能作为绕过禁止重提取边界的导入入口。

### C. 双端纵向交付

Web 与鸿蒙均完成三层体验：首屏有效条目及少量待处理项；条目详情的条件/来源/使用记录；设置里的使用、候选与处理许可。沿当前样式组织信息，来源及历史按需展开，不展示人格评分或铺满技术状态。

任务内的“为什么这样建议”可以直接纠正相关条目，返回原任务时读回真实新版本。确认失败保留输入；请求丢回包先查回执；账户切换清理或隔离草稿、缓存与导出临时文件。用户可不用候选功能继续原项目工作。

冻结旅程：用户因设备限制多次选择 CPU → Agent 只提出有条件的候选 → 用户在手机改为“仅当前课程项目” → Web 读回 → 新科研项目不继承限制 → 一条另行确认的通用偏好被原 Conversation/Mission 使用 → 用户拒绝错误候选且不再被重复打扰 → 原 Action 完成并读回 resultCardId。

### PM-2 验收与停止条件

必验 `PM-J05/08/11/13/14/16/17/23`，并回归 `PM-J04/10/22/24/26/29`。重点加入：同义改写绕过拒绝、候选确认瞬间来源撤权、丢回包换载荷、个人云处理关闭但项目允许云处理、仅项目保留却跨项目注入、导出失效历史后被自动重新导入。

以持久条目、原回执、读集和双端读回验收；不允许测试直接把候选设为 ACTIVE。先运行受影响测试，收尾完成全量回归、类型、lint、Web build/E2E、Harmony 单测/HAP；设备操作与真实模型收益单独记录。任何越权、正文残留或未确认候选消费都阻断本阶段放行。

## 十一、PM-3 执行 Prompt：长期召回与 Personal × Project Composer

> 在 PM-1 范围保护及当前 PM-2 合同之上完成 PM-3。目标是找回久远但仍适用的信息，并改变实际调查和判断；不能以“最近窗口里恰好命中一条”验收，也不引入第二套检索数据库或 Planner。

### A. 先测覆盖，再补召回

1. 读取原 `search_memory`、Digest、Hypothesis、Experience、GoalState、Conversation 与 Mission Composer。核对当前窗口、分页、索引和原文读取，不把规划里的旧数量写死为最新事实。
2. 冻结含旧有效约束、近期噪声、相似但不适用经验、撤权来源、冲突、过期与单根多摘要的独立回放集。记录当前 Recall@输入预算、决策质量、必要/多余澄清、调用量与延迟，先得到可比较基线。
3. 给长期有效条目、未完成承诺和历史综合保留可检索指针，不先截掉所有旧候选再排序。按真实查询补可重建索引，不将每份正文复制到新记忆库。
4. 继续使用原分页关键词/hybridSearch 和定向原文深读；模型按问题选择是否检索、读哪些原文以及怎样改道。资料充分时可以直接回答，不强制逐层搜索或每次固定工具链。

### B. 统一资格、选择与指纹

1. 扩展共用 eligibility/selection/manifest 服务，Conversation/Mission 保留各自编排。顺序为：认证与项目归属 → 账户政策/处理许可 → 原始来源有效性 → 当前时间/条件/冲突 → 相关性与预算；预算裁剪不能先于强制控制核对。
2. 在项目未路由前仅使用不含项目私有细节的最小账户上下文；路由确定后，再核验项目派生内容的原根和当前成员权限。不能为了选项目先读取所有项目或将私有标题放入公开 query。
3. 返回适用条目、readSet、选择原因、覆盖/遗漏及最早 `nextBoundary`。当前指令、禁止条件、权限和原责任约束不被 token 裁剪；文本与 readSet 同步裁剪，不能文本仍在而依赖被删，或以空 readSet 伪称没有个人依赖。
4. 指纹至少覆盖 owner、条目/政策/项目例外版本、privacyRevision、来源资格、时间边界、问题与条件、内容检索/选择集合版本、工具及 Composer 版本和输出受众。即使本次选中内容未变，新有效条目或未选候选集合变化也可能影响选择，不能只 hash 已选正文。
5. 可从个人段 512 tokens、最多 6 条、约占输入 10% 的初始实验配置开始；它们是可调预算，不是永久能力上限。问题需要时在原总预算内重新分配。覆盖不足要可知，不能为守固定条数丢失当前硬限制。
6. 向量是可选的可重建加速，记录 provider/model/dimension/内容及资格版本，查询和 embedding 都核对账户处理许可。不可用或不允许时回关键词与原文路径，不偷偷调用远端服务。
7. 复用原在途重协调及缓存失效。指令/条目到期、替代、撤回、跨项目迁移或来源撤权改变有效视图；没有新事件但时间越界也必须在派发/发布前挡住旧版。缓存复用限于当前授权、来源版本和条件仍成立的原始观察，不复用旧结论冒充新判断。

### C. 交互与真实行为改进

用户仍从原问题、项目页和记忆详情进入；使用依据可展开、纠正或停止使用。回读旧资料时显示当前调查动作与覆盖，不增加必须操作的检索控制台。Web 支持深查；鸿蒙能读回关键依据、短纠正和接续状态，两端共享原对象。

冻结旅程：30/90 天前的有效条件被大量新材料淹没 → 原 Agent 找回并核对原文 → 当前项目临时指令覆盖个人默认 → Agent 根据缺失划分/基线动态调整工具选择 → 从相似旧经验回读适用条件并拒绝负迁移 → 手机纠正后 Web 原任务继续 → 原批准、Action、resultCardId 与 Handoff 完整读回。

### PM-3 验收与停止条件

必验 `PM-J03/06/19/21/25/26`，回归 `PM-J07/09/11/15/16/18/24/29`。加测：输入溢出时保留硬限制；未选集合变化使选择缓存失效；同一网页衍生十份摘要仍只有一个根；相似向量但不适用；长久未完成承诺不因最近窗口被丢弃；并发到期与派发/发布屏障。

比较相同权限、工具、模型和输入预算下的旧路径与新路径。分别报召回、证据支持、调查顺序、错误/多余澄清、负迁移与成本；不能只给命中率或文风评分。真实模型质量未测时注明，不能用脚本 provider 证明智能收益。工程检查和双端验收沿 PM-2 的完整要求执行。

## 十二、PM-4 执行 Prompt：演化、Dream、Experience 与持续责任

> 在前阶段范围、召回和双端 Gate 之上完成 PM-4。目标是在既有持续责任中识别有意义的新问题，让反例改变后续判断，并控制打扰；不启动新的后台执行器，不把整理计划等同于 Always On。

### A. 原任务内的观察、假设和经验

1. 核对当前 Worker、Mission Delegation/责任合同、Investigation、GoalGap、Attention、Claim/Source Policy、AgentExperience 及结果同步。写明真实已实现与本阶段差额，不复制已交付 UX-3/CT-7～10。
2. 组织为“原观察或记忆变化 → 有版本的候选/GoalGap/Hypothesis → 核验原责任范围 → 原有界调查、建议或一次必要授权”。调查中的动态工具选择和改道保持；没有执行根、许可或预算时不启动付费整理模型。
3. 区分已授权委托与只读主动研究。只读也要有允许的范围和原预算；兴趣、个人偏好、推测和外部材料不能新建长期责任、扩大工具或批准外写。超出委托时保存有依据的建议，通过原机制请求授权。
4. Dream 整理与 Hypothesis 待验证主张分别处理；支持、反例和未知关联同一稳定主张及条件。沿原状态、来源修订与独立根判断，不能靠更多摘要把猜测积累成事实。
5. 跨项目方法只提出有条件的迁移候选，不删除 Experience 的原 projectId 或来源。确认抽象理解不解除原项目权限；数据划分、环境、协议、工具版本等缺项仍是 UNKNOWN。
6. 复用 Experience Use、反馈及原结果同步。用户采纳、满意、Action DONE、工具成功与现实效果分开；方法失败可成为反例，未知结果不能强化或反驳方法。个人偏好不因一次成败被自动重写。

### B. 唤醒、失效和有界持续运行

1. 复用原事件、计划检查、来源修订、截止时间和 Worker 恢复；新的整理触发挂原队列、幂等身份、lease 和预算根，不建立夜间 Runner 或额外常驻定时器。
2. 无变化、观察失败、来源失效、等待用户分别留下原步骤/活动/等待原因和下一次检查。无变化可以消耗获准 HTTP 检查，但不无故调用模型；失败不伪装成“没有变化”，等待用户不反复重试。
3. 个人条件变更按依赖 readSet 扇出到原任务。账户关闭/删除/撤权先由同步版本守卫阻断，再异步展开清理；不能只使当前打开的项目刷新。`nextBoundary` 接入原下次检查及派发/发布守卫，跨时界不依赖用户重新打开页面。
4. 原 Mission 的目标、成功标准、作用域、期限、总预算、工具、触发、审批和停止条件仍是责任边界。跨日预算、预约、UNKNOWN、迟到工具和 Worker 接管沿原结算；STOP/撤权后不再派发旧依赖操作。
5. 已派发外部操作不能靠删除记忆宣称撤销。沿原操作状态、幂等 key 和 readback/UNKNOWN 对账；不得重发外写换取一个确定成功状态。
6. 与 CT-7 部署观察、CT-8 Experience、CT-9 Browser/只读工具、CT-10 批准外写逐一适配当前 grant、来源版本、工具效果与回执。未配置能力标为不可用或未验收，不使用模拟工具冒充真实平台完成。

### C. Attention 与跨端责任视图

1. 重要性判断使用新变化、目标缺口、临期和可行动性；保留依据与不提醒原因，观察重要变化漏报，不能只以提醒减少为成功。
2. 去重、合并、安静时段和偏好复用原 Attention/InterventionPolicy。模型推断的关注偏好只形成候选，用户明确确认后才调用原策略服务。已读、已通知、已批准和已执行使用不同持久状态。
3. Web 展示真实已做事项、证据、成本/未知费用、等待原因、下次检查和原暂停/恢复/STOP；鸿蒙提供短回应、纠正与接续。不要额外做一套后台控制台。
4. 个人原话不自动进入项目共享提醒、Widget 或小艺；沿原 owner/session/generation/TTL 与脱敏。小艺审批回 App，后台推送、分布式接续与穿戴只按真实平台能力及设备证据声明。

### D. 三日完整验收

沿 Roadmap 第三节冻结三日旅程，不用只跑 cron 三次替代：

- D1：真实材料与已生效的个人协作方式进入原 Conversation/Mission；用户按原批准机制确认期限、工具、检查条件和累计预算。Agent 有依据地提出缺口，未确认猜测不进个人事实。
- D2：经历一次无变化、一次观察失败和一次有效新反例；原调查核对来源并改变下一步。课程临时要求覆盖默认；跨项目方法仅形成可纠正候选。Worker 中断后恢复，预算与 UNKNOWN 不重置。
- D3：手机在模型/工具在途时纠正；原 generation 拦住旧发布，合法原始观察可复用；Web 从原 Handoff 接续。用户沿原提案/批准执行 Action，完成服务写回 resultCardId；效果未知如实保留。随后暂停/删除条目和撤销来源权限，双端、后续任务及派生路径不再消费。

工程层用可控时钟、屏障和合成 provider 重现竞争，另做真实自然日观察；两类记录分开。真实用户、付费调用、外部写入和生产部署仍按具体授权范围，不因 Prompt 包含场景就直接执行。

### PM-4 验收与停止条件

必验 `PM-J07/09/12/15/18/20/27/28`，回归 `PM-J11/13/16/19/21/22/23/24/26/29`。增加同一变化跨 Web/手机/Worker 合并提醒、安静时段结束后的合法补发、失败退避与等待用户不同、无事件到期、STOP 与工具派发竞争、已批准外写后撤回、反例迟到与旧经验注入竞争。
