# 个人记忆与项目记忆：产品研究和方向裁决

日期：2026-11-01。本文与同目录其余五份文档组成专项规划。本轮做了源码审计、历史验收材料核对和公开资料检索，没有实现新功能或开展用户实验。

建议先读本文，再读 [架构审计](MEMORY_ARCHITECTURE_AND_SCOPE_AUDIT.md)、[Agent 集成](MEMORY_AGENT_INTEGRATION.md) 和 [实施路线](PERSONAL_MEMORY_ROADMAP.md)。界面方案在 [UX 设计](MEMORY_PRODUCT_UX_DESIGN.md)，下一轮可直接使用 [实施 Prompt](PERSONAL_MEMORY_IMPLEMENTATION_PROMPT.md)。所有新字段、接口、阈值和实验人数都是规划建议，未实现。

## 1. 用三个月以后，用户应该得到什么

第一天，忆程需要知道用户在做什么、有哪些材料、什么算完成。三个月以后，它应该能少问一些已经回答过的问题，发现过去的经验何时有用，也能及时放下已经不适用的认识。

例如，用户同时做课程作业、竞赛和科研。课程作业曾明确要求只用 CPU，科研项目后来可以使用服务器。忆程应该把两个项目的资源条件分开；可以记住用户明确表达的“方案先做小规模验证”，在科研项目中建议先用少量样本排查数据问题。它仍须核对这个项目的数据许可、可用设备和实验预算，不能凭过去的习惯直接启动实验。

这比记住“用户喜欢详细回答”更有产品价值：同一个偏好可能改变问题的拆解方式、首先查什么资料、什么时候需要澄清，以及下一步提出什么可执行的行动。是否确有改善，需要用任务和结果来检验。

| 使用一段时间后的变化 | 用户能看到的结果 | 验证时要排除的假象 |
|---|---|---|
| 不再反复解释稳定背景 | 新会话能沿用用户确认的背景，遇到条件变化会重新问 | 从本轮提示词偷取答案，或漏问必要条件 |
| 项目之间能借鉴方法 | 发现“先核对数据划分再比较指标”也适用于当前项目 | 把另一项目的指标、人员和数据直接搬过来 |
| 纠正会生效 | 用户改正“这只是报告中的说法”，后续不再把它当实测 | 界面显示已纠正，旧摘要和旧提案仍在使用 |
| 委托能接回原处 | 回来后能看到原目标、等待条件、已做的事和结果 | 重新创建一项相似任务，丢失原预算和回执 |
| 主动性更有分寸 | 有影响的变化才找用户，无变化时保持安静 | 多积累通知，或把观察失败说成没有变化 |
| 理解可以检查 | 重要判断能说明用到了哪条记忆，用户可就地纠正 | 只给“因为我了解你”一类无法核对的解释 |

这六项是产品假设，不是本次已经测出的收益。长期目标也不该退化为资料推荐：在用户现有许可内，忆程应能主动查原文、选工具、比较证据、修改调查方向，并把结果接回原委托。

## 2. 值得做的方向，以及暂不投入的方向

| 方向 | 用户价值 | 用户负担 | 工程成本与可验证性 | 裁决 |
|---|---|---|---|---|
| 只保存回答风格 | 立即可感知，但差异化有限 | 低 | 较低，容易验证是否遵守 | 做，作为入口，不作为全部产品 |
| 保存用户明确提供的背景、协作偏好和长期关注 | 减少重复解释，改善问题理解 | 低至中，需要范围和有效期 | 中，可用新项目任务验证 | 优先做 |
| 将多个项目中的方法形成条件化经验 | 改善调查与下一步建议，贴合项目产品 | 中，需要确认适用条件 | 中至高，要测负迁移 | 在原 Experience 上推进，先候选后迁移 |
| 自动建立完整个人画像 | 可能少问问题，也可能越用越错 | 高，用户难以逐条检查 | 高，隐私和正确性很难验证 | 不作为默认方向 |
| 把所有项目总结汇成一本“人生档案” | 看上去丰富，实际任务收益不清楚 | 高 | 高，易重复、泄露和过时 | 不投入首批 |
| 让记忆直接触发长期行动 | 自动化程度高，但授权容易漂移 | 极高 | 高，需要独立责任合同 | 记忆可发现问题，执行仍依原 Mission 许可 |

推荐的定位是：**忆程记住用户确认过、与做项目有关的背景和协作方式，并让这些认识帮助下一次调查和推进；项目事实仍留在各自项目中。**

“我希望未来做医学图像方向”可以影响问题关联和研究建议；它不是访问患者资料、读取所有项目或启动新委托的许可。“我通常不希望晚上被打扰”可以形成待确认偏好；正式安静时段仍要写入原 Attention 设置，不能由模型偷偷改通知策略。

## 3. 公开产品提供了哪些可借鉴的做法

以下是本次访问到的官方资料。产品行为会随版本、账户和地区改变；这里只采用资料明确说明的能力，不反推其内部数据库、并发协议或实际效果。文中的“借鉴”是 ProjectMemo 的设计判断。

### ChatGPT：显式记忆、历史引用和后台综合

官方 FAQ 区分保存的记忆与历史引用，提供查看和删除控制；删除聊天不自动等于删除独立保存的记忆。借鉴点是把“保存什么”和“允许使用什么”分开，删除要覆盖来源与派生内容。ProjectMemo 不照搬其留存时间，而需定义自己的清除合同。[Memory in ChatGPT](https://help.openai.com/en/articles/8590148-memory-faq)

2026 年 6 月的 Dreaming 文章描述后台综合历史、维持新鲜度与相关性，并提供可查看的记忆摘要。它没有公开足以复现的完整实现。借鉴点是更新综合、检查过时，而非把后台运行本身称为学习成功。[Dreaming](https://openai.com/index/chatgpt-memory-dreaming/)

Projects 文档说明项目指令在项目内优先，共享项目使用 project-only memory，不引用成员的项目外个人上下文。这里值得采用的是清楚的范围边界；ProjectMemo 的个人上下文也不能因进入共享项目而自动公开。[Projects in ChatGPT](https://help.openai.com/en/articles/10169521-projects-in-chatgpt)

### Claude：账户认识与项目上下文需要分层看待

当前官方帮助页同时描述新旧两种体验。新体验按主题保存记忆，项目内可结合账户记忆，并提供项目隔离控制；旧体验仍描述定期综合。不能把旧版“每 24 小时更新”当成所有账户的当前机制。借鉴点是账户记忆与项目记忆可协作，但使用开关和项目例外必须看得见。[Claude chat search and memory](https://support.claude.com/en/articles/11817273-use-claude-s-chat-search-and-memory-to-build-on-previous-context)

其 incognito 文档说明临时对话不进入普通历史和记忆。ProjectMemo 应借鉴“这次不使用、也不新增个人记忆”的明确选择，但不冒称它等同于所有审计记录都不留存。[Use incognito chats](https://support.claude.com/en/articles/12260368-use-incognito-chats)

### Muse：用户能检查记忆，执行边界仍独立存在

Meta 的技术文章描述专属云环境、可检查和下载的用户文件及记忆，以及 Agent 不能绕过的外部交互控制层。它没有公开完整的记忆晋升、纠正传播算法。可以借鉴用户可检查性与权限分离，不能据此推断 Markdown 文件天然可信，或其产品已证明长期理解正确。[How We Built Safety Into Muse](https://research.meta.ai/blog/security-and-safety-for-ai-agents-our-approach-with-muse)

### Letta：把上下文分块，但不要放开权威数据自改

Letta 文档提供持久 memory blocks，支持共享及只读设置。借鉴点是按用途划分上下文；不采用“模型能编辑一个块，所以它能改用户事实”的推论。个人理解可以由模型提出修订，生效条件仍由应用服务判断。[Memory blocks](https://docs.letta.com/v1-sdk/memory/memory-blocks)

### Mem0：提取和召回是两件事

官方文档描述消息提取、带标识存储与查询召回，应用决定哪些结果进入提示词。`user_id`、`agent_id`、`run_id` 等标识提供分类基础，不替代 ProjectMemo 的成员权限、来源版本和停止协议。其“提取事实”也不能直接对应本项目的已证实事实。[How Mem0 Works](https://docs.mem0.ai/core-concepts/how-it-works)

### LangGraph：跨线程存储不等于恢复执行

官方文档将 thread 范围的 checkpoint 与跨线程 store 分开。这个区分与 ProjectMemo 的原 Turn/Mission 和记忆内容相容，值得保留。持久化能帮助恢复状态，但不能自动解决外部操作重复执行；本项目继续使用原幂等与 UNKNOWN 对账机制。[Memory overview](https://docs.langchain.com/oss/python/concepts/memory)、[Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)

### 开源方案是否适合直接引入

把产品控制和工程机制放在一起看，可以得到下面的分工。未核实的内部传播时限不填成“实时”。

| 对象 | 范围与形成 | 查看、更新与清除 | 对本项目的启发 |
|---|---|---|---|
| ChatGPT | 显式记忆、历史引用和综合；项目有独立设置 | 用户管理，聊天与独立记忆需分开处理 | 查看摘要不能替代逐条资格与删除传播 |
| Claude | 当前主题式记忆与项目/账户使用控制；存在旧体验 | 用户可查看和编辑，临时模式有单独边界 | 版本不同不能套同一更新周期 |
| Muse | 公开资料强调用户可检查的个人记忆和隔离环境 | 文件可检查/编辑/下载；内部记忆演化算法未公开 | 可控性与外部执行权限分离 |
| Letta | 可配置的持久分块、共享与只读 | 由应用设置哪些块能改 | 认知草稿可以更新，权威政策应由服务限制 |
| Mem0 | 作用域标识、提取与召回分开 | 应用挑选进入模型的内容；本轮未核实完整清除传播协议 | 检索命中不能直接视为可信或有权使用 |
| LangGraph | thread 状态与跨 thread store 分工 | 应用定义长期条目的更新和治理 | 执行恢复与长期认识不应混为一张摘要 |

前述各行的公开事实分别对应上文的官方链接；最后一列是设计判断。它们都没有给 ProjectMemo 提供现成的用户授权、项目血缘和业务回执合同。

本次通过 GitHub 公共 API 核对了仓库元数据，以下只是 2026-11-01 的快照，星数不表示质量。

| 仓库 | Star 快照 | 许可证 | 最近推送日期 | 可以参考的部分 | 直接接入的代价 |
|---|---:|---|---|---|---|
| [letta-ai/letta](https://github.com/letta-ai/letta) | 25,314 | Apache-2.0 | 2026-10-18 | 分块上下文、后台整理与可检查性 | 引入新的 Agent 状态管理，与原 Runner 重叠 |

## 4. ProjectMemo 应保留的区别

通用助手擅长跨话题协作。ProjectMemo 值得做的部分，是把长期理解接到具体项目的材料、约束、原任务和实际结果上。

一条“先验证再扩展”的偏好，应该在当前实验资料不足时促使 Agent 去核对数据划分和基线，而不是只在回答末尾加一句“建议小步迭代”。当用户允许执行固定核算时，结果要回到原 Mission、Action 和 `resultCardId`。如果发现方法不适用，这次反例应阻止下一次无条件复用。

这要求个人记忆、项目事实和方法经验互补：个人记忆描述用户希望怎样协作、明确提供了什么背景；项目记忆描述当前项目发生了什么、哪些证据仍有效；Experience 描述某种方法在什么条件下有过什么结果。任何一层都不负责另两层的授权。

## 5. 对几个前提的独立判断

**“个人记忆越多越好”不成立。** 有效性、适用范围和被纠正后的行为，比记录条数重要。先保存少量能减少重复或改变调查路径的内容，允许用户从未启用个人记忆也正常使用项目能力。

**“Dream 就是夜间自动学习”不成立。** 当前 UX-2 的综合和假设更新主要依附原推理调用。后台整理可以补充，但要有变化触发、预算来源和可测收益。没有变化时无需额外调用模型。

**“多次采用意味着偏好”不成立。** 多次使用 CPU 可能只是当时没有 GPU；连续忽略提醒也可能是消息没送达。模型可提出有条件的候选，不能据次数直接激活永久偏好。

**“确认一次便永远正确”不成立。** 用户确认的是原话、解释和适用范围，不是证明背景永远不变。毕业、退出项目、授权撤回和时间越界都可能改变可用性。

**“自动化越多越贴心”也不成立。** 主动研究、创建委托、发送通知、批准外部写入是不同动作。记忆让 Agent 更会判断是否值得调查，但不会替这些动作提供许可。

## 6. 七个问题的回答

**为什么使用忆程的个人记忆？** 如果它能让长期背景影响真实项目调查，并把建议接到可追溯的执行结果上，就有独立价值。仅保存个人介绍和回答风格，还不足以支撑这个理由。

**两层怎样互补？** 账户层保存经过准入的个人理解；项目层保留本项目事实与责任。跨层使用需要内容范围许可和来源有效性，不复制一份项目数据库。

**用户如何感到越来越被理解？** 少重复背景，旧纠正不再重犯，跨会话接回原问题，已有习惯在适当情境下起作用；条件变了会问，而不是装作一直知道。

**如何改善执行，而非只改语气？** 验证工具选择、调查顺序、必要澄清、行动可执行性和结果回读；比较关闭个人记忆时会怎样做。只有词语更像用户，不算执行收益。

**如何建立信任和控制？** 在使用处解释重要依据，在设置中看完整条目；修改、停用、撤回与删除有不同结果，并能检查传播。暂停个人记忆后，项目资料和原任务仍能继续使用。

**哪些设计只是复杂？** 无差别画像、复杂人格分数、把所有内容画成知识图谱、另建一套后台学习 Runner，首批均缺乏足够任务收益证据。

**先投哪里？** 先打通一条完整旅程：明确保存偏好或背景，新会话和原委托能使用，用户能看到使用原因，纠正或关闭后在途与后续消费及时遵守。随后补候选理解和长时召回，再用多项目任务评估收益。
