## 1. 结论：现在最值得补什么

ProjectMemo 已有真正的调查与执行基础：Agent 可以读材料、动态选择工具、遇到新观察后改道，长期委托能等待、接续和保持累计预算；用户的修订会影响原 Turn、Mission 和待批提案；结果能进入原 Action、复盘卡、Handoff 与条件经验。

目前最大的差距发生在这些能力的两端。首次用户仍要先组织项目信息，再寻找记录和调查入口；任务运行以后，用户也不容易一次看清本次用了什么能力、哪些条件真被核对、哪些只是保存了记录，以及花费是否仍可控。大量工程能力还没有通过独立真实模型、真实设备和连续使用共同证明价值。

建议当前收尾优先完成四件事：

1. 统一 CT-7 与现有工具基线，修复旧入口的权限、原子性与隐私缺口，建立一致的能力表达。CT-7 合并已在本轮完成，其余缺口保持规划范围。
2. 用一份真实材料贯穿建项、第一次判断、手机纠正和原结果回读，形成首次可核查的价值。
3. 把现有执行回执组织成能说明项目推进的证据视图，保留未完成条件和反例。
4. 启动独立质量与三自然日验收，并把失败沉淀成版本回归。

系统分享、可靠待同步和个人记忆值得投入；完整穿戴应用、全量跨设备迁移、工具市场、多 Agent 编排和自动训练并不应挤占这一轮收尾。

## 3. First Verified Value：先让用户得到一次有依据的帮助

### 3.1 当前的阻碍

`components/NewProjectForm.tsx` 先要求项目名称、至少十字描述和目标，场景默认竞赛，截止时间可选。创建以后才进入项目，再使用 Capture、Attachment 和对话。对已经能清楚描述项目的人，这条路可用；对刚收到课程要求或老师材料的人，产品先让他做整理工作。

还有可靠性问题：`app/api/projects/route.ts` 先创建 Project，再单独创建 OWNER membership；没有稳定创建请求身份。成员写入失败或客户端丢回包时，界面重试可能留下孤儿或重复项目。这应先修复，不必等待新的首次使用设计。

### 3.2 建议的完整切片

首页提供“用一份材料开始”和原有“填写项目”两种入口。前者允许粘贴要求或选取一个文件；先在账户隔离的本地草稿中保留原内容，再提议项目名称、目标和材料归属。模型提议不能自动成为项目目标，用户可以直接编辑。确认后用原项目服务原子建立项目与 OWNER，通过原 Capture/Attachment 保存材料，再进入原 Conversation 调查。

第一份结果应包含一个对当前工作有用的判断：例如原要求中的截止时间、目前缺的验收材料，以及为什么先核对某个条件。依据必须能回到材料原文或原页；没有证据的内容留为推测。资料已经足够时不强制联网，条件缺失时允许自主追查，只有私有信息、冲突选择或授权问题才找用户。

参考 Notion Web Clipper 的地方是采集时选择归属、保存后直接打开原对象；其公开文档也说明不同来源会有解析限制。这不能证明 ProjectMemo 可以完整解析所有网页，更不能将采集成功当成理解成功。[Notion Web Clipper](https://www.notion.com/help/web-clipper)

### 3.3 成本与验收

先分别计时：材料进入草稿、原文持久保存、第一次可核查判断、用户确认有帮助。以首次判断 P50 五分钟、P90 十分钟作为先导目标，随后用实际分布校准；不在界面先承诺固定分钟数。分母包含所有开始建项的合格用户，退出、解析失败、缺少云额度单独列出，不删除困难案例来美化转化率。

规则整理也可以提供保存和结构化价值，但应显示规则模式，不能计入真实模型质量成绩。新增复杂度主要是建项事务、草稿接续和已有服务间的请求绑定，不需要新引导 Runner。默认不自动扫描用户全部文件，也不因用户上传文件而获得公开研究或后台委托许可。

## 4. Low-Friction Capture：先存得住，再谈更会理解

已有 Capture 原文、知识卡候选、稳定 requestId 和附件 hash/修订链。附件支持图片、PDF、CSV、JSON；OCR 不可用和提取失败已有状态。缺口是系统分享、项目归属前的留存、可靠待同步，以及语音的原件和校对语义。

首先修正现有 Web 草稿：CaptureBox 的 localStorage key 只有项目和用途，UserNav 退出只清理 Conversation 草稿。在共享浏览器、共享项目的情况下，前一账户的未提交内容可能被后一账户恢复。增加离线能力前，必须按 owner 隔离并验证退出与迟到写入。

建议用同一份本地采集信封承接分享和断网：本地身份、clientDraftId、原始类型/内容 hash、来源信息、候选 projectId、同步状态和原 requestId。服务端 owner 仍从认证会话取得。状态至少区分本地未提交、待登录、待归属、正在同步、原回包未知、已保存和需重新核对。回包未知先查原请求，不换编号重新上传。

来源应用传来的 projectId、标题和 URL 都是提示。用户确认归属、在线重验项目权限后才进入原 Capture/Attachment；URL 的保存不等于允许 Fetch。临时文件 URI 需要按平台授权复制到私有草稿区域，不能假设分享应用退出以后仍可读取。大文件设大小、类型、保留期和空间不足恢复；前台可靠同步先完成，不承诺操作系统一直允许应用在后台上传。

语音分两步。第一步是设备识别后让用户校对文本，再进入原 Capture；保留识别来源，不把不确定转写直接准入为长期指令。第二步才考虑保存音频、时间对齐与重新转写，此时需扩展原 Attachment 类型、存储和处理成本。系统键盘听写可作为现有文本入口的辅助，不能据此宣称已有完整语音产品。

最小验收是“外部应用分享 → 断网留存 → 重启 → 选择项目 → 在线原请求保存 → Web 读回”。以原文不丢、一个持久对象、无串账号和错误归属为硬条件；不要先优化自动归类命中率。频繁开会、做实验和接收老师材料的学生受益最大。

## 5. Outcome Intelligence：能解释推进，但不替现实盖章

### 5.1 现有边界值得保留

`resultVerifier.ts` 检查原草稿、来源数量、批准、行动或固定核算回执。`completionSummary.ts`、`presentation.ts` 和 `goalState.ts` 已分别保留内容核验、采纳、行动回执及 `NOT_INFERRED/REPORTED`。CT-8 的 TrajectoryIndex 也区分工程完成、用户自述、独立核算和明确负结果。

因此，不应把草稿型委托允许完成当成缺陷，也不应重新做结果账本。真正需要补的是把分散的记录组织成目标相关、能核对的推进说明。

### 5.2 最小结果投影

从原 Mission、Action/resultCardId、Artifact 采纳回执、固定核算和有效来源生成只读结果视图。每个判断绑定：

- 目标及验收条件版本；原任务与行动身份。
- 支持或反对该判断的来源、修订、观察时间和适用条件。
- 证明的是记录、用户报告、一次实际观察、可重复核算，还是仍待验证的推断。
- 覆盖了哪些路径、环境和时间窗口，哪些条件还没有证据。
- 下一步是否需要用户、继续调查或等待原委托中的事件。

这些是互相独立的维度，不压成一个项目完成百分比。现有参赛准备项可以继续表示清单形成比例，但不能变成项目整体成功率。

SWE-bench 的成熟做法是把模型产生的补丁放进受控仓库运行测试，而不是接受模型自报已修好。可借鉴的是独立检查实际产物；它只能证明测试覆盖内的结果，不能替代科研成效或用户项目目标的验收。[SWE-bench evaluation](https://www.swebench.com/SWE-bench/guides/evaluation/)

例如，Action 完成回执能够说明用户报告完成；固定脚本能够说明给定输入的算术结果；目标设备上的真实路径验收能够说明指定版本和窗口内的观察。只有目标要求的条件都得到相应证据支持，独立验收才能签收那一范围的目标。模型不能因工具返回成功便提升层级。

`commitActionResult` 会处理来源提醒，而 GoalState 只取最近八条行动、四份输出。验收要检查提醒已处理是否仍保留未证实的目标缺口，并定向找回与当前委托有关的较旧行动。这与原 PM-3 召回专项共用工作，不另建目标状态库。

## 6. Mixed-Initiative Collaboration：用户接手后，Agent 还能合法继续

现有 Admission、GoalGap、`ask` 分类、持续责任、generation/lease 和原暂停/输入/恢复已经提供必要骨架。新增重点应放在提问质量和交接质量，而不是再写一个固定流程。

Agent 提问前，应检查这条信息是否已经存在于获准的原材料、旧决定或原行动结果中。能够在现有许可内调查的内容继续查；只有私有信息、关键选择、确有冲突或需要扩大权限时，才问一个能推进当前判断的问题。用户可以跳过、补材料、改目标或接管，而不必把系统表单全部填完。

在任务内提供就地操作：暂停调查、补充这个条件、纠正这项理解、由我处理、回看原依据。接管回执应说明 Agent 已做过什么、哪些外部请求仍可能完成、下一次继续需要什么。用户的“我来处理”不等于任务已经达成，沉默也不等于批准。

目标变化继续使用原重协调：服务端使相关批准和消费者失效；旧模型语义不跨 generation 发布；有效原始观察可按原合同复用；已发出的未知外部效果保留 UNKNOWN 和累计消耗。停止不能保证收回已发出的 HTTP，更不能据此返还所有费用或自动补发请求。

行业可借鉴的是依据环境反馈循环、遇到边界再找人的方式；没有必要把复杂调查预编成步骤表。Anthropic 的工程文章也将这种按观察调整的 Agent 与预设工作流区分，并要求有明确终止条件。[Building effective agents](https://www.anthropic.com/research/building-effective-agents)

验收同时记录“必要问题被省略”和“已有答案仍重复追问”。只减少轮数会奖励 Agent 猜测；只增加确认则会把自主调查退化成用户逐步驱动。

## 7. Capability Truth：每个绿色状态都要说明证明了什么

### 7.1 统一能力视图

建议从原配置、认证、配额、Worker、来源和最近执行回执生成一个只读 CapabilityAssessment，供原页面按需使用，不新增监控控制台。至少分开：

| 维度 | 例子 | 不得据此推导 |
|---|---|---|
| 配置 | 已配置模型或浏览器运行时 | 当前账号可以使用、请求必然成功 |
| 资格 | 当前用户、项目、连接和用途获准 | 原许可覆盖新项目、新来源或新写入 |
| 预算 | 原总包仍有可用额度 | 货币费用已经准确核算 |
| 运行观察 | 最近有 Worker 心跳、成功扫描或任务领取 | 当前每个委托都在推进 |
| 数据覆盖 | 已读这些页、这些记录和这段时间窗口 | 未读内容不存在、窗口外也无冲突 |
| 执行结果 | 本次模型、规则、降级或 UNKNOWN | 模型质量、现实目标或设备支持已通过 |

返回 reasonCode、观察时间、适用范围与过期时间。界面先显示与当前任务有关的一句状态，再允许展开细节。缺少数据就显示未观测，不生成“全部正常”的合成结论。

### 7.2 `/health` 与 Worker

当前 `/health` 是公开存活与版本元数据，静态 capabilities 主要反映旧小艺适配合同。保留这条匿名边界；另提供鉴权后的无副作用就绪检查，覆盖数据库可读、schema/release 身份和 Worker 观察。来源健康来自原有观察与失败回执，不在打开页面或健康检查时自动付费调用模型、刷新 OAuth 或抓取所有网站。

Kubernetes 将存活、就绪和启动检查分开，适合借鉴这种语义分工；本项目不需要因此引入 Kubernetes。就绪检查也不能代替一条真实用户路径。[Probe semantics](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/)

当前 WorkerPresence 已区分心跳、扫描和领取，Web 文案也没有直接把心跳叫作调查完成。问题是本地文件对部署拓扑的依赖。若实际部署仍为一台机器，先验证两个进程读取同一个受控路径，绑定部署/版本身份，记录扫描失败和队列延迟即可。需要跨节点时，再在相同合同后加入同库租约投影；没有证据表明现在值得引入新调度平台。

### 7.3 降级与不确定结果

Capture 的规则后备应保留，原文保存也不因云失败回滚。但保存响应需要带回有效模式和恢复入口，鸿蒙服务不能继续只返回 card 而丢弃这些字段。Conversation 已有项目状态回读和 limitations，可作为一致表达的参照。原始 provider 错误不能直接显示给用户。

“已读”“已通知”“已批准”“已执行”“有结果回执”保持独立。系统没有可信投递通道时，不接受客户端自报 PLATFORM_ACCEPTED；已有 UX-3 修复继续生效。

## 8. Agent Improvement Loop：让下一版可证明地少犯错

已有 Run、Step、Event、prompt/version、用量、错误分类、ExperienceUse 和多套评测脚本。现有评测规范也已包含分母、故障轨和预算，不能因为改进闭环这个名称再建设一套评测产品。

推荐补齐这一条链：用户指出问题 → 绑定原消息/步骤/来源版本 → 记录可核对的失败分类 → 经用户同意提取最小脱敏样本 → 人工检查正确行为与反例 → 加入开发或留出集合 → 同版本预算对照 → 独立评审 → 版本回归。

失败分类至少覆盖：意图误读、遗漏必要澄清、过度提问、资料遗漏、引用不支持、适用条件错误、过期信息、跨域越权、工具选择或参数错误、未知结果恢复错误、能力误导、无效打扰、成本超限和界面恢复失败。用户不喜欢某种文风，不直接归因成工具失败；用户没采纳，也不自动成为方法反例。

默认 Trace 以原对象身份、事件、时间、版本、用量和失败码为主，正文留在已有权限域。用户选择反馈时再预览最小样本；去除凭据、个人信息、无关项目和可识别关联，并保留脱敏过程与权限。开发目录中原来保存完整合成请求的脚本不能直接用于生产用户内容。评测不得把这些正文自动发到第三方观测平台或评审模型。

代码验收、模型评分和人工评审要配合使用。研究题通常有多种合理调查路线；评分应看结论依据、覆盖、必要澄清、有效工具选择、结果与成本，不按固定工具序列给分。Anthropic 的评测文章支持组合代码、模型与人工评审，并区分能力评测和回归；这些方法仍需要项目自己的任务与标注。[Demystifying evals](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

Langfuse 的 Trace—数据集—实验—反馈组织方式、Promptfoo 的声明式评测与红队值得参考；不建议首批接入新的外传平台。先在原脚本输出相同概念的可审查文件，等维护成本有证据后再决定依赖。[Langfuse evaluation](https://langfuse.com/docs/evaluation/overview)、[Promptfoo](https://www.promptfoo.dev/docs/intro/)

## 9. Dynamic Capability & Cost：版本变化必须能被看见

### 9.1 能力清单与经验失效

现有 Tool.version、PromptSpec 和 Experience 工具/协议版本检查是正确基础。缺口在于版本可省略且默认 1，schema 或 effects 改动未必强制更新版本，也没有完整的模型能力与费率绑定。

建议为原注册表生成受控 manifest：工具名、显式版本、输入/输出 schema hash、effects、可用条件、适用连接和计费类别。模型侧记录 provider、请求与返回的模型身份、协议、prompt/schema 版本以及已知能力。CI 比较 manifest 变化，要求显式兼容性判断。

工具语义或许可改变时，相关缓存、Experience、原提案和在途消费者沿原 readSet/generation 重验；批准载荷的语义变了就不能沿用旧批准。模型升级主要影响提示词、缓存、建议质量和条件经验资格，不自动撤销原始事实。原事实的有效性仍由来源决定。

MCP 当前规范提供工具清单、schema 与 listChanged，并允许按授权返回不同能力。这是能力清单可演化的参考，不是必须接入 MCP，也不提供 ProjectMemo 的业务批准或可信度保证。[MCP tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)

### 9.2 费用合同

`monetaryCost: null` 是当前缺失信息的正确表达，不应为了展示完整改为 0。建议在原 Run/Turn/Step 的计量中绑定 rateVersion、币种、计费类别、请求身份和父任务，投影出：已知计量估算、已核对账单、未知项目、保守预占、可证明上界及覆盖。

缓存输入、普通输入、推理输出和普通输出要按 provider 的包含关系归一化，不能把总输入和其内含的缓存部分重复计费。OCR、embedding、协议修复、Judge、失败和迟到调用都需要归属；没有 token 用量的请求仍保留原未知预占。

用户设定任务预算时，先原子预占再派发，结算释放或保留原余额。费率未知、图像计量未知或第三方费用无法封顶时，只能明确使用原次数/资源上限，不能承诺严格货币上界。新增价格信息通过显式、带版本的配置进入，不让模型猜价格。

OpenTelemetry 可参考其模型、操作、用量等属性，但相关规范仍在演化；记录自己的 schema 版本，正文采集另设许可。可观测字段本身不等于财务账单。[GenAI attributes](https://opentelemetry.io/docs/specs/semconv/registry/attributes/gen-ai/)

## 10. Data Sovereignty & Security：先补实际越界路径

### 10.1 现有安全基础与新增发现

现有 SourcePolicy、来源版本、外部内容数据封装、PR-6 网络策略、浏览器隔离、外写批准和 UNKNOWN 对账应继续复用。审计同时发现旧入口并未全部拥有同样的保护：项目删除仅检查 membership；数据库级联没有串起附件文件清理；采集草稿未绑定账户；成果 Markdown 默认渲染远程图片及 preload。

最后一项说明安全边界不能只放在 Tool 适配器。模型生成的图片 URL 可能让用户浏览器隐式联网，绕过工具的域名、披露和预算合同。本轮纯 SSR 探针只使用合成 marker，证明会生成这些标签；修复后还需真实浏览器网络断言，确认预加载、图片和其他自动资源均受控。

### 10.2 可携带与清除

首批项目导出应包含用户有权带走的原文、附件/修订、当前理解及其来源、目标变化、决定、原任务、行动结果和相关回执。用 manifest 记录 schema、导出时间点、对象身份、hash、范围及缺失项。导出账户内容与导出共享项目是不同范围；项目 OWNER 不能因此得到其他成员的私有 Mission 或个人记忆。

Notion 公开提供页面、数据库和工作区导出，可作为分范围选择和格式可读性的参考。ProjectMemo 还需要补自己的来源、任务回执和权限清单，不能把一个 Markdown 按钮当作完整数据自主能力。[Export content](https://www.notion.com/help/export-your-content)

流式导出绑定权限版本，中途撤权或删除停止继续披露；凭据、认证数据、签名材料和不可访问的引用不进入包。成果 Markdown 继续作为轻量导出，不能冒充完整可携带性。

本人明确导出原始历史与 Agent 使用证据是两种用途。用户仍有原件访问权时，可将被抑制的历史导出并标记不可复用；模型不能借此重新综合或注入。来源已删除或用户已失去访问权，则不能通过导出恢复正文。

删除先同步停止后续消费、派发和发布，再清理附件文件、缓存、派生摘要、索引、导出与端侧副本。将清理任务放进原 Worker 的有界生命周期处理，保留不含正文的最小幂等/禁止重提取标记。未清除的副本及备份期限要有明确状态；删除自己的数据不自动删除外部系统对象，也不能销毁其他成员仍合法持有的共享内容。Personal Memory 的派生失效合同在账户功能上线前一并接入。

## 12. Long-Term Product Value：使用更久，应改变实际协作

第一天看是否得到一项能回原文核对的帮助；一周后看是否能接回旧问题、少重复解释；一个月后看有条件的方法是否减少错误调查，提醒是否更值得处理；三个月后看项目目标的推进和用户控制是否仍清楚。

这些评测与原 PM-5、UX-3 的用户试点共用，不建立另一套长期实验。先用 6～8 名学生做任务与可用性先导，再进入 Personal Memory 规划中的探索性队列。人数用于计划资源，不构成统计功效证明；正式比较在先导后预注册。

关键指标及其失败解释如下：

| 指标 | 计量方式 | 不能接受的替代 |
|---|---|---|
| 首次可靠价值 | 从首次材料进入到一项依据正确、对当前任务有用的判断；同时报退出与不可用率 | 保存了一张卡、返回一段流畅文字 |
| 重复解释成本 | 用户为已提供且仍有效的信息重复输入的时间/轮次；必要澄清另计 | 单纯消息变短 |
| 自主调查质量 | 留出任务的依据、覆盖、适用条件、动态改道与结论质量 | 工具数量多或固定流程全跑完 |
| 真实推进 | 原任务回执、独立结果证据与目标条件匹配；观察窗口明确 | Mission SUCCEEDED、采纳、用户自报直接等于目标达成 |
| 纠正和接续 | 纠正提交后各消费边界遵守新版本，原请求/预算/结果身份保持 | UI 隐藏旧卡或新建一个相似任务 |
| 通知价值 | 有行动价值提醒/已送达且可评提醒；另报误报、漏报、静默和观察失败 | 只降低通知数 |
| 用户信任与控制 | 能解释依据、未知和当前状态，能完成停止/纠正/删除，并记录主观信任 | 一个没有行为依据的满意度分数 |
| 成本 | 每个有用结果/完成旅程的已知费用、未知预占、模型/工具/HTTP 与延迟 | 平均 token 降低而成功率和覆盖下降 |

比较使用相同模型、材料截点、权限和预算。复用现有 Mission/Copilot 基线，再增加 Personal/Digest/Dream 的原消融；不得为了对照移除安全门。按用户和项目留出，重复试验记录稳定成功率，独立评分者不知道条件。三日时间推进用于工程状态，三自然日用于连续使用，两者分别报告。

## 14. 独立裁决

**必须进入当前收尾：** CT-7 正确整合；建项原子性和同请求恢复；删除角色、草稿隔离、远程资源控制及删除停止使用；模式/部分覆盖/UNKNOWN 的如实表达；一条真实材料到原结果的双端旅程；独立实模和三自然日验证的实际执行与分层签收。项目导出、结果投影和任务费用的基础版本应随这一轮核心旅程补齐。

**先预留合同：** 工具与费率 manifest、来源和隐私依赖、可清除的反馈样本、设备能力与导航状态、小艺分发回执、未来跨设备接续。接口预留要绑定现有身份、版本与授权，不能提前启用未验收执行路径。

**当前属于过度设计：** 第二套 Planner/Runner、平行记忆或结果账本、通用工具市场、自动模型切换与扩额、全量自动画像、生产日志自动外传评分、未验证的穿戴审批、手机常驻无限后台、没有任务收益证据的模型微调。它们不是因为技术困难而后置，而是尚未比现有缺口更能改善用户的真实项目。

## 15. 增量价值判断：从工程基础到用户能感知的协作

本轮仅复核本地代码和证据，未重新研究十个方向。主目录仍为 `1ee89f3`；PM-1～3 已在独立分支提交，PM4 与记忆入口有并行修改。PM4 最新全量日志不是全绿，真实模型/设备/自然日仍不能由旧记录推定通过。完整状态与风险进入原矩阵和 Roadmap，不另起专项路线。

八项深化的价值依赖实际行为：

| 维度 | 会让用户感到不同的行为 | 不能当成收益的替代 |
|---|---|---|
| 首次使用 | 交一份材料就得到可纠正的项目理解；接受后才建项，第一次判断能回原文 | 多一个建项总结、先建空项目、流畅但无依据的开场 |
| 长期理解 | 记得当前仍有效的旧条件，能说清个人默认与项目例外；纠正和到期真实生效 | 条目更多、向量更多、把所有偏好永久保存 |
| 自主协作 | 自行查可查材料，关键私有缺口只问必要决定；用户接管后继续原任务 | 固定工具流水线、问题数越少越好、静默猜测或越权 |
| 跨端接续 | 点卡片/手机/Web 后回到同一问题、依据和当前待处理项 | 仅打开首页、新建相似任务、把深链接当批准 |
| 结果可信 | 进展叙事关联原回执、反例、条件与未知；花费覆盖可解释 | Mission 成功等于现实目标完成、虚构节省时间和 ROI |
| 持续改善 | 失败形成经同意脱敏的独立样本，Experience 在条件对照中减少错误 | 经验条数增加、模型自评提高、自动改生产 Prompt |
| 能力恢复 | 在原许可内重评替代和覆盖；不能继续时给具体恢复条件 | 无限重试、未批准换 provider、清零预算或绕过撤权 |

这些变化有望形成可感知差异，但源码与工程数量还不足以证明收益。判断依据应是首次用户能否核对并纠正理解、多日后能否准确复述当前主焦点、必要澄清是否改善、跨端是否保持原身份、以及真实结果/未知和费用是否可核查。先执行 Roadmap 原收尾 1 的材料理解—调查—接续纵向切片，再沿原收尾 3/4 验证叙事、成本与改进。

单独改术语、界面标签、manifest 或统计口径不会自动改善体验。它们若保护了权限、来源、费用或恢复，是必须完成的工程工作；产品收益需在实际判断、维护负担、接续正确性或任务结果中另外证明。Security Gate 不因尚无可见收益而降级，Evidence Gate 也不因工程完成而关闭。
