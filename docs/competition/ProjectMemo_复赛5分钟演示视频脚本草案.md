# 忆程 ProjectMemo｜复赛 5 分钟演示视频脚本草案

> 成片目标：4 分 40 秒～4 分 50 秒，不压 5 分钟上限。
> 叙事主线：一次会议改变方案，忆程如何保留旧证据、解释变化、推动行动，并把结果写回项目记忆。
> 当前状态：脚本草案。最终录制必须使用同一提交、同一后端和同一签名 HAP；版本号、域名、账号与录制日期均为 `【待确认】`。
> 执行准备：ECS、后端、小艺、HAP 的部署与验收步骤见 [ECS、后端、小艺与 HAP 执行手册](projectmemo-ecs-backend-xiaoyi-hap-runbook.md)。

## 1. 视频只讲清一件事

传统工具记住“写过什么”，忆程进一步回答：

> **这些历史信息现在是否仍然有效，为什么发生变化，下一步应该做什么？**

视频不做功能巡游，不逐页介绍菜单。全片围绕下面一条因果链展开：

> 方案 A 显存超出设备预算 → 会议决定改用方案 B → 系统展示差异与证据 → 用户确认 → 旧方案被标记为已取代 → 系统提出下一步行动 → 用户完成实验并填写结果 → 结果成为新的复盘记忆。

评委看完应能确认四点：

1. 忆程维护的是有时态、有来源的项目记忆，而不是普通笔记列表。
2. Agent 能发现变化并提出行动，但不会绕过用户静默修改项目。
3. 每次提醒和回答都有可查看的依据，证据不足时会明确说明。
4. 行动结果会回到记忆与状态中，形成可持续的项目闭环。

## 2. 录制前硬门禁

以下条件没有全部满足时，只能彩排，不能录制“最终演示视频”：

- [ ] 最新候选提交已部署到 ECS，`/health` 返回的 release 与本地候选提交一致。
- [ ] `Constants.ets` 已切换为 `BUILD_FLAVOR = 'review'`，`REVIEW_BASE_URL` 为设备可访问的 HTTPS 地址，不是 `10.0.2.2`、`localhost` 或 `127.0.0.1`。
- [ ] 最终签名 HAP 已安装到干净测试设备；冷启动、登录、杀进程重启与网络恢复均通过。
- [ ] 演示账号、演示项目和数据仅用于比赛，不含个人真实记录、Token、密钥、内网地址或调试日志。
- [ ] 从最终 ZIP 中取出的 HAP 完整走通本脚本至少 3 次，每次不超过 4 分 50 秒。
- [ ] 最新候选提交的单元/集成测试、E2E、鸿蒙检查和构建结果已固化为回执。
- [ ] 如果视频出现小艺，已从小艺开放平台测试态真实调用，并完成 `request_id`、业务 ID 与 App 数据对账；否则使用本文默认的“纯 HAP 主线”。
- [ ] 录屏设备关闭消息通知、来电横幅和个人账号头像；状态栏时间、电量与网络状态正常。

## 3. 固定演示数据

正式录制前，用专用演示账号准备以下项目。字段名称以最终客户端为准；缺少的字段不要临场编造。

| 项目 | 固定内容 |
| --- | --- |
| 项目名称 | `轻量视觉模型复赛项目` |
| 项目目标 | `在评审设备约束下完成稳定、可复现的视觉模型演示，并形成答辩材料。` |
| 项目截止日期 | `2026-09-30`（若官方日期变化，按最终赛程统一修改） |
| 当前决策卡标题 | `方案 A：原始视觉模型` |
| 当前决策卡内容 | `当前基线采用方案 A；已有训练记录和效果截图，尚未完成评审设备显存验证。` |
| 风险卡 | `方案 A 在评审设备上的峰值显存可能超过预算，若不复测将影响现场演示稳定性。` |
| 材料要求卡 | `答辩材料需要包含方案对比、设备预算与复现实验结果。` |

### 3.1 会议更新输入

会议日期输入：

```text
2026-09-16
```

会议文本逐字输入：

```text
方案 A：原始视觉模型在评审设备上显存超出预算，改为方案 B：轻量视觉模型。
截止日期改为 2026-09-22。
行动：补做方案 B 基准实验并整理方案对比表。
```

预期预览至少出现：

- 一项“决策取代”，明确旧决策为“方案 A：原始视觉模型”；
- 一项截止日期变化，目标日期为 `2026-09-22`；
- 一项待办行动，不把“准备做”误写成“已经完成”。

如果旧决策未被唯一匹配、日期进入待澄清状态或预览项缺失，停止录制并修正演示数据；不要用剪辑掩盖失败。

### 3.2 行动完成输入

完成行动时逐字输入：

```text
方案 B 基准实验已完成：测试脚本可重复运行，峰值显存低于评审设备预算；实验日志与结果截图已归档，下一步整理答辩对比页。
```

### 3.3 问忆程输入

```text
为什么现在要优先完成方案 B 的基准实验？请给出依据；证据不足的部分明确说明。
```

预期回答必须引用当前项目中的风险、会议变更或材料要求；不得只给通用建议。

## 4. 逐秒分镜与旁白

### 0:00～0:20｜开场：项目不会突然失忆

**画面**

1. 深色纯净背景出现作品名“忆程 ProjectMemo”。
2. 依次浮现“会议 / 实验 / 代码 / 文件 / 截止日期”。
3. 切入鸿蒙端项目空间，不展示浏览器地址栏或开发工具。

**旁白**

> 一个项目最容易丢失的，往往不是文件，而是一次决定为什么发生、一条结论现在是否仍然有效。忆程 ProjectMemo 把散落的项目碎片沉淀为可追溯的记忆，并在变化发生时推动下一步。

**字幕**

```text
让项目记得为何改变，也知道下一步做什么
```

### 0:20～0:50｜项目状态：先看见“现在”

**操作**

1. 点击项目卡片“轻量视觉模型复赛项目”。
2. 停留在工作台顶部 2～3 秒，展示截止日期、当前进度、最大风险与下一步。
3. 点击“状态与变化”或对应简报入口，展示当前状态基线。
4. 点开风险所引用的原始卡片，再返回工作台。

**旁白**

> 进入项目后，忆程先给出当前状态：离截止还有多久，最大的已知风险是什么，哪些信息仍然不足。每个判断都能回到原始卡片；如果证据不够，系统会写“无法判断”，而不是补出一个完整答案。

**验收点**

- 风险与原始证据可以相互定位。
- 页面没有相互矛盾的相对日期。
- 演示数据有明确的项目归属。

### 0:50～1:50｜会议变更：先预览，再确认

**操作**

1. 点击“会议更新”或“导入会议文本”。
2. 输入会议日期 `2026-09-16`。
3. 粘贴第 3.1 节的会议文本。
4. 点击“预览影响”。等待请求真实返回后，依次展开三项变化。
5. 先展示旧决策、拟采用的新决策和截止变化，再勾选要应用的项目。
6. 点击“确认应用”。看到成功反馈后返回工作台。

**旁白**

> 导师在会议中要求停用方案 A，改用轻量方案 B，并提前完成基准实验。忆程不会直接改写项目，而是先把会议拆成三类候选变化：旧决策将被什么取代，截止日期如何变化，还需要新增哪项行动。每一项都绑定预览时的项目版本，只有我逐项确认后才会生效；如果项目已经被别人更新，旧提案不能覆盖新事实。

**字幕**

```text
变化先预览 · 影响可解释 · 用户确认后才生效
```

**剪辑要求**

可以压缩网络等待，但必须保留“点击预览—返回真实结果”和“点击确认—出现成功结果”两个因果瞬间，不能用静态截图冒充操作。

### 1:50～2:25｜变化简报：历史没有被抹掉

**操作**

1. 打开“状态与变化”简报。
2. 展示“方案 A 已被方案 B 取代”、截止日期变化和新增行动。
3. 点击“查看证据”，进入对应会议记录或决策演化链。
4. 打开记忆时间线，短暂停留在“当前有效 / 已被取代”状态标签上。

**旁白**

> 确认后，旧方案没有被删除，而是带着原因和时间留在历史里；新方案成为当前结论。变化简报只陈述两个状态快照之间真实发生的差异，阅读简报本身不会偷偷创建新的行动。

**字幕**

```text
保留历史，不让旧结论继续冒充当前事实
```

### 2:25～3:15｜主动介入：为什么偏偏是现在

**操作**

1. 返回工作台，进入与方案 B 基准实验相关的主动提醒。
2. 展开“WHY NOW · 为什么是现在”。
3. 展示触发原因、引用证据与建议行动。
4. 点击“接受建议”或最终界面中的同义按钮。
5. 跳转到行动板，确认只生成一条对应行动。
6. 点击“查可行性”，展示“可开始 / 受阻 / 无法确认”以及实际依赖。

**旁白**

> 当截止提前、设备风险仍未关闭时，忆程主动提出“补做方案 B 基准实验”。它必须回答“为什么是现在”：触发条件来自新的截止日期，风险来自设备预算，材料要求来自答辩清单。提醒有每日预算和免打扰时段；只有接受后，建议才成为行动。

**验收点**

- 提醒展示真实触发原因，不是预写死的宣传文本。
- 接受同一提醒不会重复生成行动。
- 如果依赖证据不足，页面必须显示“无法确认”，不能强行显示可执行。

### 3:15～4:00｜行动完成：结果重新成为证据

**操作**

1. 打开“补做方案 B 基准实验并整理方案对比表”。
2. 点击“完成行动”。
3. 在结果输入框粘贴第 3.2 节文本。
4. 点击“确认完成”，等待成功提示“已完成行动并写入项目记忆”。
5. 返回记忆或工作台，打开新生成的阶段复盘卡片。

**旁白**

> 完成不是把待办打一个勾。忆程要求留下结果回执：做了什么，得到什么证据，下一步是什么。提交后，行动状态与复盘卡片一起写入；即使重复点击，也不会生成第二张结果卡。项目因此获得了新的事实，而不只是少了一条待办。

**字幕**

```text
行动结果回写记忆，成为下一次判断的依据
```

### 4:00～4:28｜证据问答：能回答，也能说不知道

**操作**

1. 切换到“问忆程”。
2. 输入第 3.3 节问题并发送。
3. 展开“查看证据回执”。
4. 展示结论的支持状态和被引用的原始卡片。

**旁白**

> 此时再问“为什么要优先完成方案 B 的基准实验”，回答会引用刚才的会议、设备风险与截止变化。每条结论都标明依据是否充分；证据不足时，忆程会直接说不知道。

### 4:28～4:50｜收束：主动，但不越权

**画面**

1. 快速切过“记录—变化—确认—行动—回写”的闭环图。
2. 回到项目工作台，展示更新后的状态。
3. 以作品名和一句话创新点结束。

**旁白**

> 从一次会议，到一项行动，再到一条新的项目记忆，忆程让项目的每次改变都有来路、每次推进都有回声。它可以主动，但不越权；可以生成，但必须有据。忆程 ProjectMemo——让项目记得为何改变，也知道下一步做什么。

**片尾字幕**

```text
忆程 ProjectMemo
证据驱动的项目过程档案与决策手账
鸿蒙 ArkTS 客户端 + Next.js 项目服务端
```

片尾不要写“已正式上线”“完全离线”“已通过小艺平台验收”或“支持所有鸿蒙设备”。

## 5. 小艺镜头替换方案（仅在平台验收通过后启用）

默认成片不出现小艺。只有完成平台测试态真实调用、业务 ID 对账与多轮稳定性验收后，才用本节替换 0:20～0:50 的部分镜头。

### 5.1 对小艺说的话

```text
小艺小艺，帮我记到忆程的“轻量视觉模型复赛项目”：方案 A 在评审设备上峰值显存超出预算，需要在 9 月 22 日前完成方案 B 基准实验。
```

### 5.2 镜头要求

1. 从小艺开放平台测试态或实际允许的入口发起，不用直接调用后端脚本冒充平台调用。
2. 保留小艺返回成功结果的画面。
3. 切回忆程，在对应项目中打开刚写入的记忆。
4. 录制前在内部回执中核对同一次调用的 `request_id`、`card_id` 和 App 实体 ID；视频可隐藏长 ID，但不能跳过对账。
5. 如果平台只显示节点 `SUCCESS`，却无法在 App 找到相同实体，本镜头判定失败，不得进入成片。

**替换旁白**

> 我也可以通过小艺把现场发现直接记入指定项目。平台调用与忆程中的这张记忆使用同一请求链路；切回应用后，刚才的风险已经落到对应项目，而不是停留在一段对话里。

## 6. 拍摄与剪辑执行清单

### 6.1 画面

- [ ] 建议以 1080p、30 fps 录制；界面文字在普通笔记本全屏播放时仍可辨认。
- [ ] 统一使用最终 HAP，不混剪 Web 原型、旧模拟器包和最终真机包来冒充同一次流程。
- [ ] 手势落点清楚，每个关键结果停留 2～3 秒；长列表只滚动一次。
- [ ] 不展示 `.env`、API Token、数据库路径、服务器终端、个人通知或真实联系方式。
- [ ] 网络等待可以剪短，但关键请求前后的操作与结果必须连续可辨。
- [ ] 若使用模拟器画面，角标写“DevEco 模拟器演示”；若为真机，写明设备型号与系统版本 `【待确认】`。

### 6.2 声音与字幕

- [ ] 旁白约 230～260 字/分钟，先录干声再按语义剪画面，不用加速到难以听清。
- [ ] 背景音乐低于旁白 18～22 dB，不使用版权来源不明的音乐。
- [ ] 术语首次出现时给出中文解释；`Unknown` 统一写“未知/证据不足”，不翻成“错误”。
- [ ] 字幕逐句校对“项目记忆、已被取代、人工确认、结果回写”等核心词。
- [ ] 片尾保留 2 秒静帧，作品名、团队名和赛道方向与报名系统一致。

### 6.3 成片验收

- [ ] 总时长小于 5:00，建议不超过 4:50。
- [ ] 至少出现一次真实保存、一次用户确认、一次证据跳转和一次行动结果回写。
- [ ] 视频中的项目、日期、提醒和最终状态前后一致。
- [ ] 视频展示的提交 ID、后端 release、HAP 哈希已记录到最终 manifest。
- [ ] 若录制后修改代码、后端配置、签名包或演示数据，重新判断是否必须重录。
- [ ] 使用无缓存播放器从头到尾播放一遍，确认无黑帧、花屏、静音、错字和末尾截断。
