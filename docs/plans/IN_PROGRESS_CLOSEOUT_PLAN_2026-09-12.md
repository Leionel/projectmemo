## 1. 目标、顺序和完成口径

目标：把已有后端和部分 UI 补成用户可完成、失败可恢复、证据可追溯的完整流程。

推荐执行顺序：**S1 正确性 + M1 状态一致性 → F1 正确性 → R1 证据粒度 → T1/F1 页面 → B1 曝光 → C1 联调 → 统一设备验收**。同一时态底层只修一次，避免七个任务各建判断逻辑。

这是单人排期顺序，实际依赖如下：

| 执行包 | 对应项 | 必要依赖 | 预计有效开发时间 |
|---|---|---|---|
| E1 状态与历史正确性 | S1、M1 共享部分 | 当前基线与独立数据库 | 1.5–2.5 日 |
| E2 记忆修订闭环 | M1 | E1 的统一状态契约 | 0.5–1 日 |
| E3 逐句来源与核验 | R1 | E1；附件场景依赖 E2 | 1–2 日 |
| E4 可行性与编辑 | F1 | E1 状态契约 | 1–1.5 日 |
| E5 会议导入闭环 | T1 | E1；创建行动复用 E4 | 1–1.5 日 |
| E6 曝光与反馈 | B1 | 既有预算与干预接口 | 0.5–1 日 |
| E7 简报与设备回归 | C1、七项联调 | E1、E3；最终回归依赖所有包 | 1–2 日 |

粗估约 7–12 个有效开发日，不含设备、证书、平台等待；不是从头重做全部 P0/P1。已有修复通过回归即可抵扣。

每项保留原状态字段，并追加两列：**代码验收**、**设备验收**。两者都通过，原状态才从 IN_PROGRESS 改成 VERIFIED。设备缺失写明“代码通过、设备 BLOCKED”，不能直接全绿。R3、R4 仍独立，本文不顺带宣布它们完成。

## 3. E1：S1 快照正确性与统一时态

### 修改位置

`lib/services/projectStateService.ts`、`lib/projectState/buildSnapshot.ts`、`lib/projectState/computeDiff.ts`、`lib/types/projectState.ts`、`lib/memory/temporalLedger.ts`、`lib/repositories/temporalRelations.ts`、`prisma/schema.prisma`、对应迁移与 tests。

### 实施步骤

1. **统一时态输入。** 源数据带完整 confirmedAt、validFrom、validTo、revokedAt，以及人工确认信息；通过现有 Ledger 或共享纯函数计算。删除 Snapshot 自己把非 SUPERSEDES 关系全当 SUPPORTS 的逻辑。
2. **明确状态映射。** CURRENT 且存在明确确认来源才能形成对应有效性结论；SUPERSEDED 表示不再作为当前决策；CONFLICT/PENDING/INSUFFICIENT/REVOKED 不得兜底为 TRUE。确认来源不等于任意内容语义已证明。
3. **历史身份与内容去重分离。** 推荐为快照加项目内递增 `sequence`，唯一键改为 `(projectId, sequence)`；sourceHash 改为查询索引。仅比较最新快照的源哈希、规则版本和评估区间，相同才复用；恢复旧内容也生成新的 sequence。
4. **原子读取和写入。** loadSourceInput 接受事务客户端，同一短事务完成读取源、找最新、比较与写入；事务内不调用模型/索引/网络。并发写失败应有界重试整个事务、重读源和最新序号，不能继续写第一次失败前的缓存。
5. **稳定比较。** sourceHash 的集合按实体 ID 排序；contentHash 使用排除 observedAt/evaluatedAt 的业务投影，证据时间仍保存于 payload。Diff 同样不把时间戳或数组顺序当事实变化。
6. **迁移兼容。** 旧记录按 evaluatedAt、id 确定排序后回填 sequence，保留旧 ID 和游标引用；升级 policyVersion，旧错误 payload 不原地伪装成新规则结果。历史跨版本比较明确提示需新基线。
7. **排序统一。** latest、previous、check-in 推进全部使用 sequence，不再依赖可能相同的毫秒时间。检查完成行动、确认关系、会议写入后的刷新与失败补偿。

### 必过用例

- 同一 goal A→B→A：三条历史；最新为 A；重复刷新第四次不新增。
- 同时两个相同刷新：同一新状态只产生一条历史；游标不能倒退。
- CONTRADICTS、未来生效、过期、撤销：快照与 Ledger 一致，不显示假“当前有效”。
- 事实不变只推进一秒、改变输入数组顺序：contentHash 与业务 Diff 不变。
- 跨 deadline 边界：无需新增卡也产生正确风险变化。
- 写入成功但状态刷新失败：业务仍显示已保存，状态显示待刷新；重试不重复业务记录。
- 旧库副本迁移成功，历史 ID/游标可读；关闭功能仍能执行原核心流程。

**S1 代码通过条件**：以上断言、接口集成测试通过；设备还需验证刷新、重启、已读游标、空态与错误态。

## 4. E2：M1 修订原子性与操作入口

### 修改位置

`memoryLifecycleService.ts`、`attachmentService.ts`、`captureService.ts`、`temporalLedgerService.ts`、现有卡片详情/记忆时间线、`AttachmentCorrectionModal.ets`、lifecycle 路由。

### 实施步骤

1. 检查独立卡片的“人工确认来源”是否被时间线、搜索、Snapshot、F1 一致消费；不能只是新增审计行，读取端仍认为未知。
2. 消除附件纠错的半成功：先在事务外完成结构化生成，再在一个事务里写 Capture/Card、AttachmentRevision、取代关系和审计；索引放提交后。提取出可接受 tx 的纯数据库保存步骤，不在 SQLite 中嵌套完整 processCapture 事务。
3. 为同一修订请求保存幂等标识和原版本；重复提交返回同一新卡，原版本已经变化则提示重载。不同纠错操作不靠文本相同而粗暴合并。
4. 核对用户能完成确认、撤销、归档、恢复、查看修订前后文本。缺入口再补小型菜单/详情组件，复用现有导航。
5. 归档只影响默认检索，不改时间有效性；不得让旧方案复活。已有交付物引用保留原来源，用户另行确认转绑。

**必过用例**：确认独立卡、80→90→95 修订链、第二阶段数据库故障回滚、同请求重复提交、归档当前 B 后 A 仍失效、恢复后展示一致。人工确认标识可见，提取失败但人工核对的原件不被无条件禁用。

**M1 关闭条件**：无孤立半成功卡、修订可追溯且重复提交安全；上述流程在设备实际完成。

## 5. E3：R1 从上下文卡片升级到 claim 来源

### 修改位置

`artifactService.ts`、`lib/generators/templates.ts`、`lib/evidence/trustReceipt.ts`、成果 audit 路由、`ClaimAuditorDrawer.ets`、`common/ExportFormatter.ets` 和成果类型契约。

### 实施步骤

1. 为新成果保存版本化 `claims[]`：claimId、显示文本、正文定位、引用 cardId/原文片段/源版本、检查方式、生成时回执。已有 sourceRefs 可保留为上下文来源，但不能等同逐句支持。
2. 先覆盖确定性模板中的事实性句子，在渲染模板时同步生成引用映射；通用标题和建议不冒充事实 claim。测试至少覆盖两种实际演示成果。
3. 模型生成文本必须显式提供可校验的 claim 映射；只验证引用存在仍不够。无法确认语义支持的句子显示“相关来源，语义未核验”，不得标 SUPPORTED。
4. 手动编辑成果后，受影响句子的映射重新核验或失效；不能把旧来源直接沿用到新断言。为简化可先将编辑版本全部标需重检，保留编辑前版本。
5. audit 同时提供生成时来源与当前状态；点击 claim 只展示它的引用。当前来源已取代/撤销时明确提示，历史原文仍可查看。
6. 页面与导出使用同一结构化回执；旧成果缺 claim 映射时保留“仅有上下文引用/无法逐句回溯”。

**必过用例**：一句话引用 A/B、另一句只引用 C；无关当前卡不能支持句子；旧值被取代；人工修改数字；来源删除；旧成果；audit 网络失败及重试。不能仅靠数量大于零转为“核验通过”。

**R1 关闭条件**：演示成果逐句来源真实可点、导出一致；未核验句子明确标识；设备上能够从句子返回原成果。

## 6. E4：F1 修正判定并补依赖/估时编辑

### 修改位置

`actionFeasibilityService.ts`、`actions/feasibility/route.ts`、`ActionService.ets`、`models/Action.ets`、`pages/ActionBoard.ets`；拟新增 `ActionFeasibilityEditor.ets`。

### 实施步骤

1. 将依赖记录判定改为允许列表。确认且有效才 MET；INSUFFICIENT、CONFLICT、PENDING、缺状态为 UNKNOWN；SUPERSEDED 为 UNMET；撤销确认来源后按 UNKNOWN 处理，除非有明确失效证据。
2. 区分“需要这份资料存在”和“依赖该结论成立”；首版现有 card 依赖按后者处理，界面写清前提，避免一张存在的卡天然通过。
3. 扩充 API 支持增删依赖、修改软硬约束、设置/清空估时；校验、环检测和写入同事务执行。非法估时不得留下部分已添加的依赖。
4. 编辑 Sheet 提供当前项目的 action/card/deliverable 选择、估时输入和保存；服务器重评并返回 READY/BLOCKED/UNKNOWN。跨项目与循环依赖返回明确错误。
5. “先解决依赖”真实创建一个来源可追溯的任务并防重复；退出后再进仍可看到依赖。创建跟踪任务不等于执行依赖受阻的外部操作。

**必过用例**：未确认卡 UNKNOWN；撤销确认后 READY→UNKNOWN；依赖取消后 BLOCKED；增删/清空估时；非法输入事务回滚；循环/跨项目；重复点击；评估后源改变再查可更新。

**F1 关闭条件**：用户在 App 内即可配置并验证依赖，不能只有 API 可编辑。

## 7. E5：T1 会议文本到确认写入的完整界面

### 修改位置

复用 `meetingStateDiffService.ts`、`meetings/impact-preview`、`meetings/confirm`；拟新增 `MeetingService.ets`、`models/Meeting.ets`、`MeetingImportSheet.ets`、`MeetingImpactPreview.ets`，在 ProjectHome 已有录入入口增加“会议文本”。

### 实施步骤

1. 表单包含会议文本、会议日期/时区；临时输入在失败/关闭确认中保留。暂不加录音和转写。
2. 预览按决策、要求、截止时间、行动分类；每项展示原文片段与拟修改对象，并支持逐项勾选。
3. 日期未明确、旧决策匹配不唯一的项禁直接确认，提供补充/选择后重新预览。界面显示绝对日期，且与后端保存及 App 显示一致。
4. 编辑文本/日期会使旧 proposalVersion 失效；确认只发持久提案 ID、版本及选择集合，不能把客户端事实当权威。
5. 409 冲突保留输入并重预览；网络超时先查询/重试同一次确认以取得原执行结果，不新建提案重复写入。
6. 成功后显示实际变更 ID 与会后 Diff，返回项目页刷新；业务已保存而快照刷新失败显示“已保存，状态待刷新”。

**必过用例**：“准备做”只创建 TODO；歧义周五；无匹配旧决策；部分勾选缺依赖；取消；重复确认；修改文本；预览后旧事实变化；接口超时但事务已成功。

**T1 关闭条件**：在设备上完成“粘贴→预览→确认→实际写入→查看 Diff”，规则抽取明确标识，不宣传模型语义理解已完成。

## 8. E6：B1 曝光上报与反馈分母

### 修改位置

`interventionPolicyService.ts`、`interventionFeedbackService.ts`、现有 feedback 路由、`InterventionPolicyService.ets`、实际干预列表/详情组件；拟新增 exposure 路由与必要的数据迁移。

### 实施步骤

1. 定义 app 曝光：提醒区域至少 50% 可见并持续 1 秒；这是可调整产品口径，不是系统通知送达。先验证当前 ArkUI 可见性回调能否提供所需数据，若实现受限改用明确记录的近似口径。
2. 保存 interventionId、匿名 installationId、exposureId、客户端时间、服务端时间、channel=IN_APP；服务端校验提醒属于当前项目，幂等键避免重试重复记数。
3. 网络失败只缓存最小待上报事件并有界重试；不要因此阻止用户接受/忽略提醒。首次曝光口径按 interventionId+installationId 去重，原始多次曝光可单独保留。
4. 反馈关联提醒与安装身份；统计接受/延期/忽略时按唯一提醒计数，无反馈单列，不用后端 FIRE 数冒充曝光数。
5. 验证偏好建议的确认、撤销、恢复默认确实写策略版本；检查多项目预算、静默、延期和新证据重新评估。
6. 功能开关关闭时给明确状态或隐藏不可用控件；不能整页一直加载或把 503 当成“今日没有提醒”。

**必过用例**：滚动未看到不计曝光；停留达到阈值计一次；快速返回/重复上报幂等；断网重试；两项目共享预算；跨午夜；系统通知 UNSUPPORTED 不记送达。

**B1 关闭条件**：一条真实 App 曝光能在日志中对齐反馈，分母可复算，策略设置在重启后保留。

## 9. E7：C1 与统一设备收尾

### C1 专项

修改 `projectChangeBriefService.ts`、`ProjectChangeBrief.ets`、`ProjectStateDiffSheet.ets` 和状态游标入口。

1. 基于 E1 修复后的两个确定快照生成简报；每句带 changeKey 及可打开的 evidenceRefs。只有 evidenceCount 不足以让用户追溯。
2. 第一次为基线，无变化不填充“有进展”；字段恢复原值必须显示新变化。规则升级与业务变化分开。
3. 点来源能打开准确卡/行动/交付物；来源不存在显示缺失，不跳到全项目列表冒充命中。
4. 点击“已了解”才推进当前安装的游标；刷新、打开、关闭简报均不偷偷吞掉未读变化。
5. 简报失败可重试且保留旧已读点；读取简报不创建行动。

**C1 关闭条件**：设备完成“旧游标→发生变更→简报→证据→已了解→重开无重复”，并覆盖无变化、冲突、过期与失败。
