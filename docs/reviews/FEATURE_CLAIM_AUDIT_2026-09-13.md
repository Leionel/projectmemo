# 功能宣称与实际实现核对

基准：77342ff，核对 App 内 FeatureGuide、JudgeRebuttalModal、服务代码和当前运行情况。没有将原计划中的待办当作已发布宣传；本轮未修改业务代码。

## 应立即收窄的宣称

| 宣称与出处 | 当前证据 | 判断与建议 |
|---|---|---|
| FeatureGuide：“离线确定性引擎无需网络即可运行” | MemoryService、ActionService 等仍调用 ApiClient，后端地址为 10.0.2.2:4400；规则引擎在 Next 后端 | 鸿蒙端完整离线未实现。改为“无需模型 API，仍需连接项目服务”；若要离线使用须另做端侧存储、执行和同步 |
| FeatureGuide：“随手记文字、拍照或传 PDF” | ProjectHome 仅发现 PhotoViewPicker 图库选图，无相机拍摄流程 | 当前可支持选择图片，不能据代码确认内置拍照。改为“文字、选择图片或上传 PDF”；系统选择器是否提供额外相机能力需设备验证 |
| FeatureGuide：“归档（可恢复的展示偏好）” | MemoryLifecycleService.restore 存在，但页面搜索未见恢复调用和已归档列表入口 | 后端有能力，鸿蒙用户恢复闭环未接完。补“已归档”列表及恢复操作后再算用户可用 |
| JudgeRebuttal：“每一个成果章节与行动建议均有底层知识碎片强校验”“无证据不生成” | templates.ts 含固定产品描述/建议；模板只给部分卡片条目绑定 claim；模型成果保存为 UNMAPPED_MODEL；并非每章节每建议都有语义证明 | 绝对化宣称不成立。改为“记录可关联来源，部分模板事实提供引用映射；未映射或未核验内容明确标注” |
| JudgeRebuttal：“时间戳、操作人员与消融对照清晰可验” | 回执与卡片有时间和来源，但不能保证每个输入都有实际操作人员或消融实验 | 不能从存在字段/抽屉推导实际证据齐备。改为“展示已有原始记录；缺失信息标记待补” |
| JudgeRebuttal：“自动识别冲突并建立取代链，批量将旧待办作废，确保…杜绝脏数据” | 变更是预览后用户确认；匹配有规则边界，连续附件修订仍有已复现伪冲突 | 写成“生成变更候选，由用户确认受影响对象后更新”；删除“杜绝”等保证措辞 |

## 部分实现或当前不可用

| 能力 | 现状 | 可使用的准确口径 |
|---|---|---|
| 记录文字 | 有录入/保存代码，但当前模拟器点击＋记录不出面板 | 当前入口故障，修复并提交一条测试记录后验收 |
| 状态基线/每次变化对比 | 后端已有实现与回归；当前运行中 refresh 返回 HTML 404 | 代码实现与运行可用分开，当前 App 状态面板不可用 |
| 每条变化点开证据 | 简报有 entityId，但点击回调仅传 entityKind | 当前只能跳类别，具体证据定位未完成 |
| 附件旧值不冒充当前值 | 已做修订链，但连续三次纠错使最早版本 CONFLICT，见本轮审查探针 | 有版本保留，时态读取仍需修复 |
| 行动估时可清空 | UI 发送 undefined，被 JSON 丢弃，服务器保留旧值 | 设置已实现，清空操作存在缺陷 |
| 所有提醒遵守预算/静默 | agentContextService 仅在 INTERVENTION_BUDGET_ENABLED 开启时应用策略，默认 false | 应显示策略是否启用，不能无条件承诺；本轮不推断运行进程实际环境变量值 |
| 曝光与反馈闭环 | 现在采用列表加载近似曝光；跨项目队列存在丢失路径 | 不能声称已测用户确实看见，也不能据此直接报告真实曝光有用率 |

## 不能混为“没实现”的能力

- 系统即时通知已有 publish 调用；未来时间提醒明确返回 UNSUPPORTED。可以称“具备即时通知调用”，不能称“已完成系统定时提醒/关闭 App 后持续主动推进”。
- Widget 已明确标示示例，onUpdateForm 使用 buildFormData 默认值，没有真实项目同步。因此是示例看板，不是已验收的实时项目卡片；已标示例的部分不再按伪造实时数据指控。
- JudgeRebuttal 已标示内置范式，是静态功能说明，不是动态评委问答工具。问题在说明内容过度承诺，不应沿用旧结论称其完全未标演示。
- 小艺平台对账与真实用户验证尚无本轮通过回执，不能说代码完全没写，也不能说真实集成/用户效果已经完成。
- 语义检索 README 已说明需配置 embedding provider，未配置会 fallback；不能因默认走关键词就说代码不支持语义检索。
- README 仍把鸿蒙客户端列为后续路线，与已有 App 相矛盾，属于文档过时，应更新而非据此判断客户端不存在。

## 处理顺序

先修核心入口和 refresh 404；同时修改用户可见的离线、拍照、全量证据强校验等过度表述。随后补归档恢复、证据具体定位和已发现的修订/估时缺陷。最终逐项标为“可用 / 需配置 / 示例 / 未完成”，不要将设计目标与当前交付混写。
