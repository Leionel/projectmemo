## 三、 关键系统架构决策与设计规范

### 1. 证据真实性准则 (Truthfulness First)
- **禁止客户端臆造事实**：严禁在任何生产或发布代码中使用“写死日期”、“按序号推导日期”或“默认假事实兜底”；
- **缺失如实说明**：若证据链或上下文缺少准确的发生时间戳，一律明确显示“时间未知”或“证据不足”，以此建立科研及竞赛评审专用的高度可信感；
- **演示数据显式标注**：凡是通过规则测试或评委演示注入的情境，必须带有 `isSimulated: true` 标识，并在 UI 显著位置打上“模拟场景”标签。

### 2. 写操作与 Copilot 交互的服务端双重幂等机制
```
[Client]                [copilotService]                [actionService]               [Database]
   |                           |                               |                          |
   |--- 确认执行工具提案 ------>|                               |                          |
   |    (sourceRunId, kind)    |-- 检查 sourceRun.resultJson --|                          |
   |                           |   已记录该提案?                |                          |
   |                           |   [是] 直接返回存量 actionId ->|                          |
   |                           |   [否] 取存证 payload -------->|                          |
   |                           |                                |-- 开启 $transaction ---->|
   |                           |                                |   检查 action 状态已完成? |
   |                           |                                |   [是] 返回存量复盘卡 -->|
   |                           |                                |   [否] 创建复盘并更新 -->|
```
- **提案防篡改 (Trust Guard)**：客户端仅作为触发指令的载体，不得覆盖执行参数中的核心安全字段（优先级、到期日等）；
- **事务内幂等锁**：避免将“幂等检查”放置在事务外部导致并发时序空窗，确保即使网络瞬时抖动、用户快速连击，也绝对不会向数据库写入冗余脏记录。

### 3. 系统通知与平台异步能力的解耦与真实反馈
- **拒绝“假定时”投递**：OpenHarmony 标准通知接口中，`deliveryTime` 仅代表通知卡片所附的时间戳，并不具备未来定时触发器的调度能力。在未接入华为系统代理提醒（ReminderAgent）前，禁止调用 `publish` 来伪装未来的到期提醒；
- **权限与状态双解耦**：将“业务侧标记稍后处理成功”与“系统级硬件提醒已安排”解耦。如果权限被用户禁用，应提示“稍后处理已记录，但系统通知权限未开启”，不得向用户承诺无法兑现的系统提醒。

## 五、 2026 复赛决胜增量功能交付报告 (A + B + E + 鸿蒙特色)

### 1. 模块 A：决策变更影响预览与时态闭环 (Change Impact Preview & Temporal Ledger) —— 【主推核心】
* **痛点场景**：参赛过程中导师突然变更技术路线（如“显存超标，方案 A 改为轻量方案 B，截止提前 2 天”），传统工具只能手工改动零散待办，导致旧待办继续执行、交付物断言滞后的混乱。
* **交付内容**：
  * **数据契约**：[`lib/types/decisionImpact.ts`](../../lib/types/decisionImpact.ts) 与 [`harmonyos/entry/src/main/ets/models/DecisionImpact.ets`](../../harmonyos/entry/src/main/ets/models/DecisionImpact.ets)；
  * **后端分析与提交服务**：[`lib/services/changeImpactService.ts`](../../lib/services/changeImpactService.ts)；
    - `analyzeChangeImpact`：基于底层知识库和时态取代关系（`SUPERSEDES`）识别待废弃的旧决策，自动检索关联旧方案的未完成待办行动（建议 `CANCEL`）及引用旧方案的成果（建议 `REGENERATE`）；
    - `confirmChangeImpact`：在 SQLite 事务中原子执行——创建新决策卡片、建立 `SUPERSEDES` 关系、批量将旧待办置为 `CANCELLED`、自适应生成新待办；
  * **API 路由**：
    - `POST /api/projects/[id]/decisions/impact-preview`（预览受波及单）
    - `POST /api/projects/[id]/decisions/confirm-change`（事务提交原子闭环）
  * **鸿蒙端实现**：
    - 客户端：[`harmonyos/entry/src/main/ets/services/DecisionService.ets`](../../harmonyos/entry/src/main/ets/services/DecisionService.ets)
    - 对比评估弹窗：[`harmonyos/entry/src/main/ets/components/ChangeImpactDialog.ets`](../../harmonyos/entry/src/main/ets/components/ChangeImpactDialog.ets)，红绿对比呈现新旧决策、波及待办勾选框与波及成果提示；
    - 工作台接入：在演示情境控制区提供【⚡ 模拟方案突发变更 (模块 A)】一键呼出，操作后触发项目全量静默刷新；
  * **测试**：[`tests/changeImpact.test.ts`](../../tests/changeImpact.test.ts)（2 项测试通过）。

### 2. 模块 B：答辩证据核验与评委质询透视镜 (Claim Auditor & Judge Rebuttal) —— 【主推配套】
* **痛点场景**：竞赛评委在成果陈述时常质询指标提升的原始来源，或提出档案中未包含的偏门问题诱发 AI 幻觉。
* **交付内容**：
  * **证据透视抽屉 (`ClaimAuditorDrawer.ets`)**：
    - 在成果阅读器顶部提供【证据透视】按钮，点击呼出抽屉卡片；
    - 穿透展示底层引用的每一张实验与决策记忆卡片、记录时间戳、摘要原文，以及**时态有效性状态标签（🟢 当前有效 / 🔴 已被新方案取代）**；
  * **评委质询透视镜 (`JudgeRebuttalModal.ets`)**：
    - 在成果顶部提供【评委质询】入口，预设 4 项答辩高频犀利质询（如：方案变更旧待办如何处理、指标提升原始记录何在、边缘低功耗实测有无、如何证明无 AI 幻觉）；
    - 针对未实测问题，系统给出**【确凿拒答 · 严守底线】**（如：“经系统检索当前档案，无极低功耗实测数据，不提供未经检验的虚构断言”），以可信和诚信赢得评委极大信任。
