## 二、执行不到位的具体问题

### P0：先阻止错误承诺与数据污染

1. **“系统提醒已安排”仍是假成功。** `harmonyos/entry/src/main/ets/services/NotificationService.ets:130-132` 只有“将来接入 reminderAgentManager”的注释，随即返回 `success:true,status:'SCHEDULED'`。`pages/InterventionDetail.ets:111` 据此显示安排成功。移除了错误的未来 publish，但没有实现定时调度，原 ASYNC-01 未关闭。未接入时应明确返回不支持/仅业务延期，实际调用成功并取得调度凭据后才可报告 scheduled。

2. **附件校对把虚构指标预填为可保存正文。** `components/AttachmentCorrectionModal.ets:23`：附件无提取文本时，默认填入“5.8GB、34ms、98.4%”；`:37` 将其交给真实 correct API。用户按一次保存就可能将示例沉淀成项目事实。应为空白输入或单独演示数据，禁止默认混入真实附件。这个问题重新引入了原审计要消除的证据失真。

3. **决策变更确认缺少真实提案校验和项目边界。** `lib/services/changeImpactService.ts:7,108` 保存 Map，但 `confirmChangeImpact:112-200` 从不读取核对，只在结尾 delete。任意 proposalId 都能提交；supersededCardId 未验证所属项目。隔离实测：伪造 ID 被接受，项目 A 的新卡能 SUPERSEDES 项目 B 的卡。再次提交又生成不同新卡。必须持久化提案，绑定项目/原事实/允许操作、有效版本与执行结果；确认只消费经过展示的允许集合。当前取消行动的 updateMany 有 projectId 过滤，不能笼统称所有操作都跨项目；问题已证实在卡片关系边界。

4. **变更新卡的数据类型破坏后续行动闭环。** `changeImpactService.ts:132-134` 对 Prisma Json 数组再次 `JSON.stringify`，实际存入字符串。`lib/repositories/cards.ts:16` 只是类型断言，不会把字符串转换回数组。隔离场景中完成行动两次均报 `TypeError: card.keywords.filter is not a function`；干净项目同样操作通过。应按既有 capture 数据契约写数组，补“确认变更→新行动完成→复盘”的纵向测试，并评估已写入的错误类型记录。

### P1：功能完成度和可信展示不足

5. **影响分析把宽泛关键词当作所有待办失效的依据。** `changeImpactService.ts:30-41` 没匹配就选任意活跃卡；`:55-69` 只要输入含“方案/作废/提前”，所有未完成待办都列为 CANCEL，且默认 confirmed=true。隔离测试里“模型方案 A 改 B”会把“报销差旅费用”列为作废候选。应只从来源关系/明确实体判定影响，不能匹配就提示不确定；默认不勾选不明确项。

6. **成果影响只做列表提示，没有成果更新闭环。** `changeImpactService.ts:75-91` 无条件取最新 3 份成果，并称其引用前提已变更；确认接口没有成果写入，也没有修改截止日期。`ChangeImpactDialog.ets:81-87` 的新任务只是固定“跟进新决策…”模板和 priority 1。可称规则原型，不能称精准章节影响、自然语言日期更新和自适应任务规划已经完成。

7. **Copilot 幂等只解决顺序重复，没有解决并发。** `lib/services/copilotService.ts:291-338` 的检查、createAction、保存 executedProposals 相互分离。隔离并发两次确认均成功，产生 2 个待办。交接说“事务内幂等锁、绝对不会冗余”不属实。需在数据库层绑定唯一 proposal 执行记录，并将创建与结果登记原子化；同时测试同一 run 的不同提案并发，防 JSON 映射覆盖。

8. **证据透视镜并未核验当前成果的引用与时态。** `pages/ProjectHome.ets:3238` 传入整个项目 cards，而不是当前 artifact 引用集合；`components/ClaimAuditorDrawer.ets:105` 起按“超标/方案A”字样判定被取代，不读已确认/撤销的时态关系。名称含方案 A 不代表失效，其他名称也可能已被取代。`common/ExportFormatter.ets:44-46` 同样猜状态，且另一套规则还加了“原方案”，两处甚至不一致。必须接入真实 citation/claim 到 card ID 的映射和决策账本状态。

9. **评委质询是预写 FAQ，不是检索与拒答能力。** `components/JudgeRebuttalModal.ets:25-59` 预写四条答案，包括“经系统全面检索”“每项核心断言均通过 ref 锚定”等无运行依据的声明。新增或删除真实 MCU 实验也不会改变答案。应明确标为演示说明，或接入真实 Copilot 与证据回执；用有证据、无证据、冲突三个场景验收。

10. **桌面卡片是静态样板，未同步项目，也没打通待办深链。** `entryformability/EntryFormAbility.ets:8-14` 固定 2 天、80%、固定待办；`:20` onUpdateForm 为空。WidgetCard 点击仅传 targetTab:2，没有 projectId；EntryAbility 当前只处理 notificationProjectId/notificationInterventionId，未消费 targetTab。交接的“实时同步、直达对应项目待办”不成立。需要真实项目绑定、更新与失效状态、完整路由参数；分别验证添加、更新、重启和点击。

11. **附件纠错仅完成“文本→新卡”，未完成宣称的原件对照、证据修订与交付物绑定。** `lib/services/attachmentService.ts` 的 correctAttachmentText 每次创建新卡并更新附件文本，未处理旧错误卡的撤销/取代，没有写入 DeliverableEvidence。校对弹窗无真实原图/PDF 对照。当前可称文本补录功能，不能称高置信纠错闭环。应保留原始提取与人工修订记录，处理旧卡状态，并让用户明确选择交付物关联。

12. **带存证导出只是复制 Markdown，不是防伪验证。** `ExportFormatter.ets:52` 的 `PM-VERIFY-时间戳` 无内容摘要、签名或核验入口。应移除“防伪校验”措辞，或建立可以按版本/内容 hash/引用 ID 实际核验的机制；序号附录也不能代替正文 claim 引用。

### P2：旧问题修复还应收尾

- `ProjectHome.getEvidenceCandidates:499` 仍只取前 5 个候选，没有完整候选搜索入口；改善了首条自动确认，但不能说所有证据都可选。
- `ProjectHome.loadAllData` 对附件失败仍 catch 成空数组，随后覆盖 attachments，可能又让失败收件箱消失；里程碑保留历史缓存已改，附件没有等价处理。
- `ActionBoard.ets` 仍未加 onBackPress，自定义完成弹层未完整纳入返回修复；新页面已有拦截不代表全 App 验证完毕。
- `EvidenceSpineView.extractTimeLabel` 会用 evaluatedAt 代替无时间事实的时间。日期已不再写死，但评估时间应标“本次检查时间”，不能让用户误以为它是历史事实发生时间。
- 网络 10→30 秒只缓解时限不匹配，不保证所有后端请求都 15 秒内完成，也没有任务查询/幂等恢复。因此 NET-01 不宜直接判为彻底关闭。
- 新弹窗里的模块代号、长英文标题、硬编码卡片颜色与表情、关闭图标语义需做原生界面收尾；大字体、深色、键盘与读屏没有本次设备证据，不认定已经失败或通过。

1. 先移除假 SCHEDULED、默认实验数字、关键词时态判断和“已检索/防伪”无依据文案。功能未接入就明确不可用，保留真实能力。

3. 修 Copilot 并发幂等，再做影响分析的关联约束与人工逐项选择。测试无关任务、无可取代卡片、提案被篡改/过期/重复/并发。
