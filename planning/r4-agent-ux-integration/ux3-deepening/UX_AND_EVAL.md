# UX-3 R2：交互、完整三日旅程与验收

## 1. 核心交互：交代、了解进展、必要时协作

保持现有四项主导航。在焦点内提供原委托的“持续跟进”集合／筛选，不另建一套通知中心。用户默认看到当前最重要的一件事：目标、真正的等待原因和一个合法动作。

责任预览使用人话，例如：

> 到周五，围绕目标设备演示继续核对这份资料和已授权仓库。  
> 可以读和分析，在总额度内自行选择工具；需要材料或执行批准时找我。  
> 22:00–08:00 保持安静，普通结果留在这里。

数字、来源、期限和执行边界来自真实原合同，不能用示例代填。明确区分“检查当前提交”和“跟踪分支新提交”，以及“继续调查”“停止提醒”“停用来源”“撤销持续许可”。

## 2. Web 与鸿蒙

| 页面／时机 | Web | HarmonyOS |
|---|---|---|
| 第一次委托 | 原目标／标准、范围和总包预览；复杂条件展开 | 同一合同的简明摘要，必要字段可核对；复杂编辑可展开，不默认强制换端 |
| 回来了解进展 | 当前责任、变化、原结果、下一检查；按需打开活动 | 一项重要变化或待答问题，快速补材料／结果 |
| 运行／等待 | UX-1 WorkState＋真实已完成步骤，停止易达 | 同一状态／责任方，不以动画表示后台一定健康 |
| Activity 详情 | 原观察、失败、恢复、费用／UNKNOWN、provider 和来源版本 | 先给简明经过，再读原证据／回执 |
| 协作 | 原问题、具体批准、改方向、预算／来源差异 | 原已支持且 allowedActions 有效的回答／暂停／撤回／批准；保留草稿，服务端重验，不因端名推定权限 |
| 无变化／失败 | 无变化按需显示核对时间；失败说明未核对成功 | 不刷一条“没有变化”的通知；离线缓存标历史 |
| 跨端接续 | 同 Mission/claim/Action/resultCardId；旧页面显示需重读 | onPageShow／边界重读；换账号清缓存；不自动提交旧草稿 |

活动示例必须由真实记录组成：“检查了两次，同状态；最近一次请求状态未知，尚未重复发出。”不能由模型凭记忆编计数。“本月用了多少”要标已知值／预占／估算上界，不能把 UNKNOWN 隐藏在完成数里。

GenUI 继续按任务组合已有证据、变化、问题、比较、批准、回执和时间线；不固定增加七张后台控制卡。依据、未知和恢复条件放在相关事项附近。停止始终易达，诊断留详情。

### 2.1 小艺、卡片与潜在穿戴

小艺当前测试身份＋allowlist 的 inspect/resume 继续按原低风险条件；私人有界调查不能因为语音一句“继续”自动扩大许可。卡片沿现有 owner/project/TTL 和 Want 导航，打开 App 后重新认证／解析。

正式小艺身份、系统级后台投递与穿戴单独设备 Gate。当前 module 未声明 wearable，私人 Mission 无 system push，不能标“已支持”。端侧能力不足只阻塞该渠道，Web/App 主旅程继续验证。

## 3. 完整三日纵向旅程

这是原同一 Mission 的连续工作，不是每天创建一份新任务。自然日研究和工程快进分别留证。

| 时间 | 观察／用户行为 | Agent 的合法自主推进 | 原身份和回执 |
|---|---|---|---|
| D1 上午 | 用户交代“周五演示前持续核对”，核对 CI／资料范围、期限、总包、安静时段 | 自主读原材料、判断缺口，记录相关假设；获准后继续固定提交观察 | m1、责任版本 r1、h1、原来源／预算 |
| D1 晚间 | 没有重要变化，进入静默 | 检查按许可进行，稳定结果零模型；不重复通知 | 原观察步骤、下一检查、私人 inbox |
| D2 上午 | 新提交／新实验数据到达 | 若选择了分支发现才读取新 head；比较条件，更新 h1 和综合，动态改调查路径 | 同 m1；新 source/claim revision，不自动采纳 commit |
| D2 中午 | 一次观察失败／UNKNOWN；worker 重启 | 已知失败按原策略退避，UNKNOWN 保留请求；成功步骤合法复用 | 原 operationId／Step、预算和恢复事件 |
| D2 夜间 | 关键问题临近期限，用户未打开 App | 按原静默／预算政策入队或获准打断；保持问题可见，不伪造系统送达 | 原 Decision、AVAILABLE／真实平台回执 |
| D3 手机 | 用户改“先稳演示”，补设备结果，必要时批准固定核算／原行动 | 原指令／认知失效传播；迟到旧模型不再发布；继续合法部分 | 同 m1、新责任版本；原批准与 Action |
| D3 Web | 读回结果和剩余缺口，选择继续／暂停／结束 | 原结果进入 Memory Evolution／Hypothesis；完成标准据证据评，不把自报当独立核验 | 同 Action/resultCardId；原 readback 和 h1 历史 |

工具链不限于 CI。论文、PDF、CSV/JSON、Search/Fetch 可以在预算范围内自由组合；证据充分时可结束，不为了演示“自主”多读或强制核算。原工具质量 Gate 仍分别继承。

## 4. 可靠性冻结场景

| ID | 竞争／故障 | 硬断言 |
|---|---|---|
| A-J01 | Conversation 持续积压＋READY Mission | 原 worker 公平领取，Mission 不被短路饿死；不是启动第二执行器 |
| A-J02 | 两 worker 同时扫描／领取／释放 | 同一次 wake 效果和步骤不重复；epoch/lease 真正拒绝旧执行 |
| A-J03 | 同状态 CI、条目换序、时间戳变化 | 无信息时零模型、零重复提醒；原 HTTP 计费不消失 |
| A-J04 | 观察失败与无变化各一次 | 失败不标 no-change；保留 last known/freshness，有限 backoff |
| A-J05 | 截止、STOP、撤权与 HTTP／模型在途竞争 | 无新派发；迟到结果结算不发布旧提案；UNKNOWN 不重发 |
| A-J06 | 进程在请求前／发出后／落库后／发布前退出 | 原请求／步骤恢复；不复制 Mission 或清预算 |
| A-J07 | 静默跨夜、时区变化、预算日边界且无新事件 | 有效资格重新计算；STOP 不复活；总包不重置 |
| A-J08 | 同事项来自 Anchor/GoalQuestion/Focus/私人任务 | 用户预算只扣一次，消息合并，待决对象不误消费 |
| A-J09 | 一端 SEEN，另一端持旧批准；离线／换账号 | SEEN 不批准；原版本拒绝旧操作；私人内容不串账号 |
| A-J10 | 同 SHA 换连接／ref、撤权和新 head 迟到、普通 304 刷新 | 授权身份与观察 CAS 分开；旧候选／快照不自动重新授权；未来原地重授另验 |
| A-J11 | 一个坏来源／任务反复失败 | 退避和记录，不饿死其他任务，不掩盖整体不可观测 |
| A-J12 | claim/digest 到期或纠正，旧 wake 仍在队列 | 原 reuse/intent/source guard 生效，重新协调后才继续 |
| A-J13 | 额度耗尽／未知预占／用户增加总包 | 只增加明确总额，已用和 UNKNOWN 保留；无暗中新增 campaign |
| A-J14 | 卡片／小艺／通知权限关闭、账号失效 | 最小缓存与原 App 回流；没有平台证据不说已送达／可审批 |

UX-3A 先做 A-J01/02/04/05/06/10/11/13；B 补 A-J03/10/12 与真实研究；C 补 A-J07/08/09/14；D 在一条三日旅程联合验证。内部阶段不代替最终整体验收。

## 5. Agent 质量与主动性评测

工程通过之外，评分要检查 Agent 是否持续围绕原目标、正确识别变化价值、在许可内自主推进，并在必要时找到用户。

| 指标 | 定义 | 要求 |
|---|---|---|
| 责任保持 | 跨会话／天后目标、标准、scope、剩余承诺是否准确 | 不以记忆摘要覆盖新指令；跨项目污染硬例 0 |
| 自主推进 | 有资料、许可、预算时实际完成必要调查／机会数 | 不靠反复询问用户提高正确率；不奖励无意义工具数量 |
| 发现价值 | 新问题是否有出处、与目标相关、可行动／可验证 | 将猜测当事实、网页当授权均失败 |
| 变化适应 | 新观察后合理换工具、问必要条件或结束 | 按允许下一步集合评，不规定固定 Workflow |
| 注意力精度／漏报 | 有用打断／全部打断；遗漏关键可行动事项／应可见事项 | 重复提醒和关键漏报工程硬例 0；不能靠静音取得高分 |
| 接续成功 | 原 Mission/claim/Action/resultCardId 保持与无重复效果 | 工程 100%；目标用户旅程单列 n/N |
| 成本与等待 | 根模型／工具／HTTP／UNKNOWN；ready 到领取、有效变化到协作 | 各段分别记录 p50/p95；SLA 根据真实 slice/部署探针冻结 |
| 误完成／误送达 | 用户是否误把 CI、草稿、自报、SEEN 或通知接受当效果 | 硬负例 0；真实用户误解逐例修订 |

对照保持同一模型、工具和总包：当前有界委托；增加责任／活动／注意力；再加 UX-2 记忆与假设联动。可用 2×2 区分记忆和主动协作收益，预算不足时先冻结样本和优先假设，不自动删掉完整能力目标。

首轮建议质量门槛：预先标注的合法自主推进机会中完成率 ≥80%，主动发现的相关／可验证建议比例 ≥80%，用户可独立接续的旅程 ≥80%；关键可行动问题在工程硬例中可见率 100%，跨项目污染、未授权扩权、误完成为 0。门槛是待实施的试点放行标准，首次实模运行前冻结样本、评分说明和分母，不能看完结果再改。人评同时记录理由、分歧和 n/N；5 名用户只能支持试点决策，不声称代表总体人群。

没有合理新问题的无变化样本中，正确行为是继续保持责任且不制造建议；有明确有用证据的样本中，全部静音或反复让用户指定工具都算失败。盲评不给模型名称／实验组，不用实现者自评代替独立质量。

至少三类项目、5 名目标用户、跨 ≥3 自然日；独立人员准备隐藏多轮题和双人评分。模型裁判辅助，执行由原账本／SQL／回执核对；工程虚拟时钟、真实模型、自然日、目标设备和生产部署分别报告。

## 6. 实施范围与放行

复用原 mission-worker、runtimeStore、delegationObservation、investigationDelegation、Continuation、Continuity、ImpactJob、Attention/Anchor、WorkState、Web Mission/Focus 和 ArkTS 对应组件。必要增量限于责任合成版本／修订、wake 元数据、公平领取、原账本内的来源发现、只读 Activity 与真实 presence、去重与端侧适配。

CT-7～10 的新 adapter 各自交付，沿同一责任合同接入。没有 Browser 或外部写时仍应完成当前工具的完整三日接续；不能无限延期为“只是聊天”。

最终放行包括原长期委托／CI、动态调查、注意力和双端完整旅程，全部 reliability 硬例及质量评测；只接定时器或只出活动页面不算完成。设备／真实用户条件不足继续其他工程，但相关 Gate 保留，不用 HAP 和截图代替。

先通过现有 delegation feature gate 和用户白名单灰度，UI capability 明示合同版本，不能由新 UI 静默启用后台许可。关闭新增主动发现时停止新派发，保留原责任、事件、水位、消耗、UNKNOWN 和已提交回执；原仍有效的固定 CI 委托按原合同处理。新旧 JSON 版本读取、空库迁移和旧库副本升级均需验证，不能通过删除状态回滚。

### 6.2 实施前探针与未冻结参数

已从源码确认原服务／组件、预算／租约／回执和扫描入口存在；尚未验证的是持续积压下的实际延迟、wake 水位竞争、真实进程恢复、长期额度测算、正式系统渠道及自然日质量。先用原进程和独立库验证公平性／丢唤醒／UNKNOWN，再冻结 scan/slice SLA 和有限总包配置。若现有部署监控可提供等价 presence，复用它；若不能，才增加无调度语义的最小记录。

这些参数不阻碍本轮合同和旅程冻结，也不能被包装成已实现或已通过。遇到条件不足只保留相关 Gate，其他工程验证继续。
